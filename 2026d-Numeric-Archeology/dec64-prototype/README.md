# dec64 — точный десятичный тип в машинном слове

Расширение PostgreSQL: точный тип с фиксированной точкой, 18 значащих цифр,
до 7 знаков после запятой, 8 байт, передаётся по значению.

Написано как экспериментальная проверка к разбору
[fixed-point-for-postgres.md](../fixed-point-for-postgres.md): можно ли воспроизвести
схему DuckDB'шного `DECIMAL` в PostgreSQL и сколько это даст против `numeric`.

**Короткий ответ: ×17 на сложении, ×10 на умножении, ×17 на сравнении, при полном
совпадении результатов с `numeric`.**

> ⚠️ Это исследовательский код, а не готовый к эксплуатации тип. Ограничения — в конце.

---

## Представление

Значение — один `int64` в `Datum`:

```
	биты 0..2	масштаб, 0..7 — знаков после запятой
	биты 3..63	мантисса, знаковая, |m| <= 10^18 - 1
```

Значение равно `мантисса / 10^масштаб` — та самая форма `n × 10⁻ˢ` из подраздела 4.5.2
стандарта SQL.

```
 typname | typlen | typbyval | typalign | typstorage
---------+--------+----------+----------+------------
 dec64   |      8 | t        | d        | p
```

**Почему масштаб внутри значения, а не в typmod.** Output-функция типа получает только
значение: `dec64_out(dec64)`. Typmod-aware вывода в PostgreSQL нет вообще, `typmodout`
печатает сам typmod, а не значение с его учётом. Значит значение обязано уметь напечатать
себя само. Ровно поэтому `numeric` держит `dscale` в значении, `money` берёт масштаб из
`lc_monetary`, а `fixeddecimal` — из `#define`. Typmod `dec64(p,s)` при этом поддержан,
но как ограничение при присваивании — как у `numeric`.

**Почему 18 цифр.** Не компромисс, а требование: `totalDigits=18` в ISO 20022
(`ActiveCurrencyAndAmount`) и `decimal(18,2)` в формате 1С DirectBank. Три бита под
масштаб оставляют 60 бит мантиссы, `2^60 = 1.15·10^18` — ровно 18 цифр.

**Почему нет второго яруса `dec128`.** `pg_type.typlen` — одно значение на тип, а не на
typmod, поэтому ярус int16/int32/int64/int128 из DuckDB внутри одного типа невозможен.
А 16-байтовый тип не может передаваться по значению — `Datum` восемь байт, — и это
съедает почти весь выигрыш. Роль широкого яруса играет `numeric`: в него уходят агрегаты.

## Что взято у DuckDB

| решение | DuckDB | dec64 |
|---|---|---|
| Представление | масштабированное целое | то же |
| Масштаб сложения/вычитания | `max(s1,s2)` | то же |
| Масштаб умножения | `s1+s2` | то же |
| Переполнение | ошибка, тип не расширяется | то же |
| Агрегаты | накопление в 128 битах | то же |
| NaN, ±Infinity | нет | нет |
| Масштаб результата умножения выше потолка | ошибка | ошибка |

Правило «операторы остаются в своём ярусе, агрегаты поднимаются» PostgreSQL применяет к
целым (`int4 * int4 → int4` с ошибкой переполнения, `sum(int4) → bigint`), а DuckDB —
к decimal, с комментарием в коде: *«we don't automatically promote past the hugeint
boundary to avoid the large hugeint performance penalty»*. Здесь оно же.

## Где сознательно разошлись с DuckDB

**Деление.** DuckDB возвращает `DOUBLE` из любого деления с участием decimal:

> «Division of fixed-point decimals does not typically produce numbers with finite decimal
> expansion. Therefore, DuckDB uses approximate floating-point arithmetic for all divisions
> that involve fixed-point decimals and accordingly returns floating-point data types.»

Для типа, весь смысл которого — точность денежных величин, молча отдавать двоичную
плавающую точку из `total / count` — ловушка. `dec64 / dec64` остаётся `dec64`, считается
на максимальном масштабе и округляется half-away-from-zero — правило, которого требуют
регламент ЕС 1103/97 ст. 5, HMRC и п. 6 ст. 52 НК РФ. Масштаб результата зависит только
от типа, но не от данных, поэтому один запрос не может дать разный масштаб на разных
строках. Нужен DuckDB'шный вариант — есть явное приведение к `double`.

```sql
SELECT '10.00'::dec64 / '3'::dec64;   -- 3.3333333, тип dec64
```

## Что умеет

**Арифметика.** `+ - * / %`, унарные `+ -`, `abs`, `sign`.

**Сравнение.** Полный набор операторов, btree- и hash-опкласс, `sortsupport`.
Значения, равные по величине, равны при любом масштабе, и **хешируются одинаково** —
перед хешированием значение канонизируется, иначе хеш-джойн терял бы строки.

**Агрегаты.** `sum`, `avg`, `min`, `max`. `sum`/`avg` копят в `__int128` и возвращают
`numeric` — сумма по многим строкам закономерно перерастает 18 цифр. Есть
`COMBINEFUNC`/`SERIALFUNC`/`DESERIALFUNC`, поэтому работает частичная агрегация в
параллельном плане.

**Приведения.** В обе стороны с `numeric`, `smallint`/`integer`/`bigint`, `real`/`double
precision`. Приведение `numeric → dec64` — **двухаргументное**, то есть получает целевой
typmod: иначе значение сперва округлялось бы до 7 знаков, а затем до объявленного
масштаба, и `0.4449` в `dec64(10,2)` дало бы `0.45` вместо `0.44`. Двойное округление в
денежном типе — не вопрос вкуса, а дефект.

**Смешанная арифметика с целыми.** `amount * 2` остаётся `dec64`. Приведения из целых
сделаны assignment, а не implicit, — иначе `amount < 10` стало бы неоднозначным между
`dec64 < dec64` и `dec64 < numeric`.

**Округление.** `round`, `round(x,n)`, `trunc`, `trunc(x,n)`, `ceil`, `floor`, `scale`.

**Функция поддержки планировщика.** Голая десятичная константа в SQL — это `numeric`,
поэтому `amount > 5.00` разбирается как `dec64 > numeric`. `prosupport`-функция на этапе
планирования проверяет, представима ли константа в `dec64` точно, и если да — переписывает
вызов в одноимённый одно-типовой оператор:

```
EXPLAIN SELECT count(*) FROM t WHERE v > 5.00;
   Index Cond: (v > '5.00'::dec64)          -- переписано

EXPLAIN SELECT count(*) FROM t WHERE v > 5.000000001;
   Index Cond: (v > 5.000000001)            -- не представимо, общий путь
```

Это ровно то, что DuckDB делает при связывании оператора, только средствами, которые в
PostgreSQL уже есть. Без него сравнение с литералом было бы **в 1.7 раза медленнее**
`numeric` — построение `Numeric` на каждую строку дороже самого сравнения.

## Измерения

> PostgreSQL 20devel, Apple M4 Pro, 20 000 000 строк, значения 0.00…9.99,
> `jit=off`, один поток (кроме отдельной строки), лучшее из 3 прогонов.
> Сборка и запуск: `make && make install && make installcheck`.

| запрос | `numeric(18,2)` | `dec64(18,2)` | `money` | выигрыш |
|---|---|---|---|---|
| размер отношения | 692 MB | 692 MB | 692 MB | — |
| `count(v)` — скан | 430.1 | 412.3 | 428.6 | — |
| `sum(v)` | 604.7 | 435.1 | 407.2 | ×1.4 |
| `sum(v+v+v+v)` | 2809.9 | 567.9 | 521.9 | ×4.9 |
| `sum`, 8 сложений | 5067.0 | 692.3 | 649.3 | ×7.3 |
| `sum(v*v)` | 1259.3 | 491.7 | — | ×2.6 |
| `sum(v*v*v)` | 1879.3 | 548.6 | — | ×3.4 |
| `sum((v+v)*v-v)` | 2695.5 | 593.6 | — | ×4.5 |
| `ORDER BY v LIMIT 10` | 831.3 | 389.8 | — | ×2.1 |
| `count(*) WHERE v > 5.00` | 610.6 | 423.0 | — | ×1.4 |
| `GROUP BY v` | 1784.3 | 1169.1 | — | ×1.5 |
| `sum((v+v)*v-v)`, 2 воркера | 980.5 | 213.4 | — | **×4.6** |

Стоимость самих операций — вычтен скан, поделено на число операций:

| операция | `numeric` | `dec64` | `money` | выигрыш |
|---|---|---|---|---|
| сложение | 29.0 нс | **1.75 нс** | 1.38 нс | **×16.6** |
| умножение | 41.5 нс | **4.0 нс** | — | **×10.4** |
| сравнение | 9.0 нс | **0.54 нс** | — | **×16.7** |

Три вывода.

**Хранение масштаба в значении стоит примерно ничего.** `dec64` отстаёт от `money`, у
которого масштаба в значении нет вовсе, на 0.37 нс — около 27 % на операцию и ничто в
абсолютных числах. Оценка «масштаб в значении съест большую часть выигрыша», сделанная по
результату Feng Tian (×2 у decimal64 на decNumber, 2015), не подтвердилась: те 2× были
свойством библиотеки, а не дизайна.

**Точность бесплатна.** Одинаковый размер отношения, одинаковое время скана. Точный
десятичный тип не стоит ни байта против чего угодно другого той же ширины.

**Но узкое место — скан, а не арифметика.** Даже самое тяжёлое выражение даёт ×4.6.
Строчное хранилище остаётся строчным: ускорять арифметику в 17 раз осмысленно ровно до
той точки, где она перестаёт доминировать.

## Корректность

`make installcheck` — регрессионный набор на ~240 строк SQL: ввод-вывод и его отказы,
typmod и его нарушения, все арифметические операции и их переполнения, сравнение,
хеширование, приведения, округление, агрегаты (в том числе параллельные), btree- и
hash-индексы, переписывание константы планировщиком, бинарный ввод-вывод.

Ключевая проверка — совпадение с `numeric` до последней цифры:

```
   sum    |        avg         | min  | max  | count
----------+--------------------+------+------+-------
 49950.00 | 4.9950000000000000 | 0.00 | 9.99 | 10000   -- dec64
 49950.00 | 4.9950000000000000 | 0.00 | 9.99 | 10000   -- numeric
```

И классика:

```sql
SELECT '0.1'::dec64 + '0.1'::dec64 + '0.1'::dec64 - '0.3'::dec64;  -- 0.0
SELECT '0.70'::dec64 * '1.05'::dec64;                              -- 0.7350
```

Второе — расчёт налога из Decimal Arithmetic FAQ Майка Каулишо: `double` даёт
`0.73499999999999998667…` и после округления «до цента» теряет копейку на каждой
транзакции.

Набор поймал два настоящих дефекта, оба уже исправлены:

1. **`ORDER BY` мог упасть.** Выравнивание масштабов при сравнении делалось в 64 битах, и
   `999999999999999999` рядом с `0.0000001` в одной колонке давало «value out of range» —
   при том что ответ вполне определён. Сравнение переведено в 128 бит. Арифметика при этом
   по-прежнему обязана ошибаться: точная сумма этих двух значений требует 25 цифр.
2. **Двойное округление** при `numeric → dec64(p,s)`, описанное выше.

## Чего нет

- второго яруса `dec128` — сумма выходит в `numeric`;
- кросс-типовой **арифметики** с `numeric` и с плавающей точкой (сравнение есть,
  арифметика требует явного приведения);
- `sum`/`avg` с обратной переходной функцией, то есть оконные агрегаты с подвижной рамкой
  пересчитываются с нуля;
- функций вида `power`, `sqrt`, `log` — для денежного типа они и не нужны;
- поддержки 32-битных сборок: тип обязан помещаться в `Datum`, что проверяется
  `StaticAssertDecl`;
- расширенной статистики и селективности сверх стандартных `scalarltsel` и компании.

Это примерно та рутина на ~190 операторов, о которой речь в разделе 12.2 разбора: на
порядок величины выигрыша она не влияет, но отделяет прототип от типа, который не стыдно
эксплуатировать.

## Сборка

```sh
make PG_CONFIG=/path/to/pg_config
make install
make installcheck
```

По умолчанию `PG_CONFIG` берётся из `$HOME/pgdev-upstream/tmp_install/bin/pg_config`.
Требуется компилятор с нативным 128-битным целым (`PG_INT128_TYPE`).

```sql
CREATE EXTENSION dec64;
CREATE TABLE ledger (amount dec64(18,2), rate dec64(10,7));
```
