# Разрешение полиморфных ссылок в реляционных базах данных

Вспомним главную страницу типичного интернет-магазина, например WB. Лично у меня на этой странице видна реклама нескольких позиций для покупки:

- Аэрогриль
- Магний Цитрат + Б6
- Протеиновые брауни

и т.д.
Думая как разработчик баз данных, я примерно представляю себе, что эта страница - результат выполнения запроса вида:

```sql
SELECT name, description FROM products p
  LEFT JOIN kitchen_appliances ka ON (p.id = ka.id)
    LEFT JOIN pharmacy f ON (p.id = f.id)
	  LEFT JOIN sportish_food sf ON (p.id = f.id)
	  ...
ORDER BY p.popularity DESC
LIMIT N
```

Эффективно спланировать такой запрос непросто, что (по моему опыту) подтверждают репорты пользователей из мира 1С.

## Паттерн

Строка заказа может ссылаться на физический товар, цифровую загрузку, подарочный сертификат или подписку.
Запись о действии в CRM-системе может быть связана с контактом, компанией или
сделкой. Запись журнала аудита может относиться к любой сущности в системе.

В реляционных схемах нет встроенного механизма для подобных ссылок. Наиболее
распространённый способ кодирования использует **дискриминированный внешний
ключ** — пару столбцов, которые совместно идентифицируют целевую таблицу и
строку в ней:

```sql
CREATE TABLE order_lines (
    id          SERIAL PRIMARY KEY,
    order_id    INTEGER NOT NULL REFERENCES orders(id),
    item_type   VARCHAR(20) NOT NULL,   -- discriminator
    item_id     INTEGER NOT NULL,        -- polymorphic FK
    quantity    INTEGER NOT NULL
);
```

Здесь `item_type` может содержать значения `'product'`, `'gift_card'` или
`'subscription'`, а `item_id` хранит первичный ключ соответствующей таблицы.
Ни одно ограничение внешнего ключа не способно обеспечить ссылочную целостность
сразу для всех трёх целевых таблиц, поэтому ядро СУБД трактует `item_id` как
обычный целочисленный столбец.

Для разрешения ссылки — например, для получения читаемого имени того элемента,
который был заказан, — запрос должен выполнить соединение с каждой из возможных
целевых таблиц, ограниченное дискриминатором:

```sql
SELECT
    ol.id,
    COALESCE(p.name, g.name, s.name) AS item_name
FROM order_lines ol
LEFT JOIN products      p ON ol.item_type = 'product'
                          AND ol.item_id = p.id
LEFT JOIN gift_cards    g ON ol.item_type = 'gift_card'
                          AND ol.item_id = g.id
LEFT JOIN subscriptions s ON ol.item_type = 'subscription'
                          AND ol.item_id = s.id;
```

Для каждой строки `order_lines` не более чем одно из трёх левых внешних
соединений находит совпадение; остальные два возвращают NULL. По мере роста
числа типов целевых таблиц растёт и веер LEFT JOIN-ов. Данная форма запроса
далее именуется **паттерном разрешения полиморфных ссылок**.


### Структурные инварианты

Рассматриваемый паттерн обладает точной структурой, отличающей его от
произвольного набора внешних соединений:

1. **Взаимное исключение.** Предикаты дискриминатора в условиях соединения
   попарно дизъюнктны: для любой строки базовой таблицы предикат дискриминатора
   не более чем одного соединения принимает значение «истина». В приведённом
   примере предикаты `item_type = 'product'`, `item_type = 'gift_card'` и
   `item_type = 'subscription'` не могут одновременно быть истинными для одной
   строки. Это гарантирует, что для каждой строки базовой таблицы совпадение
   даёт не более чем одно левое внешнее соединение. Следует отметить, что если
   значение дискриминатора строки не представлено ни одним соединением в запросе
   (например, `item_type = 'coupon'` при отсутствии соответствующего соединения)
   или дискриминатор равен NULL, то ни одно соединение не находит совпадения —
   строка проходит через все соединения с NULL-значениями во всех столбцах
   целевых таблиц. Инвариант формулируется как «не более одного», а не «ровно
   одно».

2. **Уникальность ключа внутренней стороны.** Ключ соединения на стороне
   каждой целевой таблицы является её первичным ключом. Это проверяемо планировщиком запросов по метаданным
   каталога (уникальные индексы). В сочетании со взаимным исключением данное
   свойство гарантирует, что каждое левое внешнее соединение порождает не более
   одного совпадения на строку базовой таблицы, и, следовательно, ни одно
   соединение не дублирует строки.

3. **Ограничение на использование столбцов.** Каждое обращение к столбцу
   целевой таблицы T_i — в списке SELECT, предложении WHERE, ORDER BY, HAVING
   или любом другом предложении запроса — находится внутри выражения COALESCE
   или CASE, которое принимает значение NULL, если дискриминатор не
   соответствует T_i. Ни один столбец целевой таблицы не используется вне такого
   свёртывающего выражения. Более того, каждое свёртывающее выражение должно
   содержать столбец-вклад от каждой целевой таблицы, участвующей в левом
   внешнем соединении в данном запросе: если COALESCE включает `p.name` и
   `g.name`, он должен включать и `s.name` — за исключением случая, когда
   соединение с подписками вообще не вносит столбца в данное свёртывающее
   выражение. Это требование полноты обеспечивает, что удаление
   несовпадающего соединения не изменяет результат свёртывающего выражения
   ни для одной строки базовой таблицы.

Перечисленные три инварианта совместно влекут следующее свойство, составляющее
основу оптимизаций, разрабатываемых в последующих главах.

**Утверждение (устранение соединений при полиморфном разрешении).** *При
выполнении инвариантов 1–3 для подмножества строк базовой таблицы,
отфильтрованного условием `discriminator = c_k` (соответствующего целевой
таблице T_k), левые внешние соединения со всеми прочими целевыми таблицами T_i
(где c_i ≠ c_k) могут быть удалены из плана выполнения без изменения ни одной
выходной строки.*

*Набросок доказательства.* Рассмотрим произвольную строку r из
отфильтрованного подмножества. По свойству взаимного исключения (инвариант 1)
условие соединения для каждого T_i (i ≠ k) принимает значение «ложь» на r,
поэтому левое внешнее соединение с T_i порождает NULL для всех столбцов T_i.
По свойству уникальности ключа (инвариант 2) такое NULL-дополнение не
дублирует r. По ограничению на использование столбцов (инвариант 3) каждое
обращение к столбцу T_i находится внутри свёртывающего выражения, принимающего
значение NULL при отсутствии совпадения с T_i. Удаление соединения с T_i
исключает NULL-вклад T_i из каждого COALESCE или CASE; поскольку COALESCE
пропускает NULL-аргументы, а CASE — несовпавшие ветви, результат выражения не
изменяется: оставшиеся аргументы по-прежнему содержат вклад T_k, что
гарантировано требованием полноты. (Если совпадающей строки в T_k не
существует — случай «висячей» ссылки, — то вклад T_k сам равен NULL, и
свёртывающее выражение возвращает NULL вне зависимости от наличия остальных
соединений — тот же результат, что и в исходном запросе со всеми
соединениями.) Поскольку сказанное справедливо для каждой строки
отфильтрованного подмножества, соединения с T_i могут быть удалены из плана
для этого подмножества целиком. На уровне плана выполнения удаление
соединения означает, что узлы Var, ссылающиеся на столбцы удалённого
отношения, теряют источник данных. Поэтому преобразование заменяет каждый
такой Var на NULL-константу соответствующего типа — то есть в точности на то
значение, которое LEFT JOIN породил бы для несовпавших строк. Данная замена
сохраняет семантику как выражений COALESCE (пропускающих NULL), так и
выражений CASE, проверяющих столбцы целевых таблиц (чьи ветви вычисляются
в «ложь» при NULL-значении столбца). ∎

Следует подчеркнуть, что утверждение устанавливает гарантию удаления
*для конкретного значения дискриминатора*: при заданном фильтре
`discriminator = c_k` несовпадающие соединения могут быть отброшены.
Использование этой гарантии одновременно для всех значений дискриминатора —
без необходимости формировать отдельный план для каждого значения — представляет
собой центральную задачу оптимизации, рассматриваемую в последующих главах.

Данное утверждение относится к случаю плоского SELECT. Когда запрос
полиморфного разрешения встроен в более крупный запрос с GROUP BY или
агрегатными функциями, взаимодействие между устранением соединений и семантикой
агрегатов требует дополнительного анализа. В настоящей работе рассматривается
случай без агрегатов; взаимодействие с агрегатами отмечается как направление
для дальнейших исследований.

В ряде систем — в частности, в крупных ERP-платформах — дискриминатор
представлен не одним столбцом, а парой или тройкой столбцов, кодирующих схему,
таблицу и идентификатор строки целевой сущности. Структурные инварианты
сохраняются без изменений; меняется лишь арность дискриминатора.


### Обнаружение паттерна

Для того чтобы оптимизатор запросов мог использовать перечисленные инварианты,
он должен обнаружить их в дереве запроса. Уникальность ключа внутренней стороны
проверяется непосредственно: планировщик может удостовериться в наличии
уникального индекса на ключе соединения внутренней стороны по метаданным
каталога. Взаимное исключение требует распознавания того, что условие каждого
LEFT JOIN содержит предикат равенства, сравнивающий один и тот же столбец
(или кортеж столбцов для многоколоночных дискриминаторов) базовой таблицы с
различными константами (или кортежами констант). Например,
`ol.item_type = 'product'` в одном соединении и `ol.item_type = 'gift_card'`
в другом. Планировщик проверяет попарную дизъюнктность, убеждаясь, что
константы (или кортежи констант) различны, а столбец (или столбцы) базовой
таблицы совпадает во всех условиях соединения.

Проверка ограничения на использование столбцов требует инспекции всех
предложений запроса (списка целей, WHERE, ORDER BY, HAVING) и подтверждения
того, что каждый узел, ссылающийся на столбец (внутренне — Var) атрибута
целевой таблицы, находится исключительно внутри выражения COALESCE или CASE
(внутренне — CoalesceExpr или CaseExpr), в котором каждая ветвь извлекает
столбцы ровно из одной целевой таблицы и каждая целевая таблица, вносящая
столбцы, представлена ветвью. Конкретный алгоритм обнаружения и его интеграция
в планировщик PostgreSQL описаны в последующих главах; данный раздел
устанавливает инварианты, которые детектор должен верифицировать.


## Области применения паттерна

Рассматриваемый паттерн широко распространён в различных прикладных областях и
фреймворках. Он встречается в двух различных формах, которые совпадают по
структуре на уровне запроса, но различаются на уровне свойств схемы.

**Полиморфные ассоциации (без ссылочной целостности).** Фреймворк Ruby on Rails
популяризировал термин «полиморфная ассоциация», реализуемую как пара столбцов
`_type` / `_id` в ссылающейся таблице
(Ruby on Rails Guides, 2024;
https://guides.rubyonrails.org/association_basics.html). Объявление внешнего
ключа невозможно, поскольку целевая таблица различается для каждой строки.
Когда запросу необходимо разрешить ссылку, ORM генерирует LEFT JOIN-ы,
ограниченные дискриминатором, ко всем таблицам-кандидатам. Библиотека Django
`django-polymorphic` использует тот же подход и документирует порождаемые им
накладные расходы на количество запросов
(django-polymorphic Documentation, 2024;
https://django-polymorphic.readthedocs.io/en/stable/performance.html).
Инженерное руководство GitLab прямо запрещает эту форму, ссылаясь на потерю
ссылочной целостности и деградацию производительности запросов, наблюдаемую в
продуктивной среде
(GitLab Documentation, 2024;
https://docs.gitlab.com/development/database/polymorphic_associations/).

**Наследование таблиц через соединение (со ссылочной целостностью).**
Стратегия `@Inheritance(strategy = JOINED)` в Hibernate размещает каждый
подкласс в отдельной таблице, первичный ключ которой является одновременно
внешним ключом к родительской таблице. Дискриминатор хранится в родительской
таблице. При загрузке базовой сущности Hibernate генерирует LEFT OUTER JOIN-ы
ко всем таблицам подклассов в иерархии. В обсуждениях на форуме сообщества
Hibernate документируются случаи генерации запросов с 30–40 LEFT OUTER JOIN-ами
для иерархий умеренной глубины
(Hibernate Community, 2020;
https://discourse.hibernate.org/t/hibernate-joined-inheritance-onetoone-too-many-left-outer-joins/4625).
Подробный анализ стратегий наследования Hibernate, включая JOINED-стратегию и
порождаемую ею проблему множественных соединений, приведён также в
(Habr, 2017; https://habr.com/ru/articles/337488/).
Мультитабличное наследование Django порождает аналогичную структуру. В отличие
от формы с полиморфными ассоциациями, наследование через соединение
предусматривает ограничения ссылочной целостности между родительской и дочерними
таблицами, однако форма запроса разрешения остаётся идентичной.

Механизм наследования таблиц PostgreSQL (`INHERITS`) представляет собой
частичное решение той же проблемы на уровне схемы: запросы к родительской
таблице автоматически включают строки из дочерних таблиц без необходимости
явных соединений. Однако `INHERITS` имеет существенные ограничения — механизм
не обеспечивает ограничения внешнего ключа на дочерних таблицах, не
распространяет уникальные ограничения на всю иерархию и плохо взаимодействует
с некоторыми оптимизациями планировщика, — что ограничивает его применимость
для данного сценария. Анализ эффективности наследования таблиц в PostgreSQL
и связанных с ним ограничений проведён в работе Сорокина (Сорокин В.Е.,
«Об эффективности наследования таблиц в СУБД PostgreSQL» // Программные
продукты и системы;
https://cyberleninka.ru/article/n/ob-effektivnosti-nasledovaniya-tablits-v-subd-postgresql).

**CRM-платформы.** Salesforce предоставляет полиморфные поля поиска (`WhoId`,
`WhatId`) для объекта Activity. Одно поле `WhatId` может ссылаться на Account,
Opportunity, Campaign или любой из десятков пользовательских объектов. Salesforce
предлагает оператор `TYPEOF` в SOQL специально для обработки полиморфного
разрешения без необходимости явных соединений для каждого целевого типа
(Salesforce SOQL Reference, 2024;
https://developer.salesforce.com/docs/atlas.en-us.soql_sosl.meta/soql_sosl/sforce_api_calls_soql_relationships_and_polymorph_keys.htm).

**ERP-системы.** Платформы планирования ресурсов предприятия повсеместно
кодируют перекрёстные ссылки между документами посредством дискриминированных
внешних ключей. Когда запись главной книги может ссылаться на счёт-фактуру,
заказ на закупку, платёж или ручную проводку, ссылка хранится как пара
«тип–идентификатор». Отчётные запросы к таким схемам содержат от восьми до
двадцати LEFT JOIN-ов, ограниченных дискриминатором.


## Свидетельства стоимости в реальных системах

Количественные эталонные тесты, изолирующие накладные расходы паттерна
полиморфного разрешения, в рецензируемой литературе встречаются редко.
Количественная оценка предлагаемых в данной работе оптимизаций представлена в
главе, посвящённой экспериментальной проверке, которая следует за главами об
оптимизациях. Вместе с тем сообщества разработчиков и документация фреймворков
предоставляют существенные качественные свидетельства того, что стоимость
реальна.

На форуме сообщества Hibernate регулярно появляются обсуждения, в которых
разработчики сообщают, что загрузка одной сущности из иерархии с
JOINED-наследованием порождает запросы с десятками LEFT OUTER JOIN-ов и что
эти запросы доминируют во времени отклика при нагрузках с преобладанием чтения
(Hibernate Community, 2020). Документация django-polymorphic посвящает
отдельный раздел вопросам производительности, рекомендуя разработчикам
использовать `.non_polymorphic()`, когда конкретный тип не требуется
(django-polymorphic Documentation, 2024). Запрет GitLab на полиморфные
ассоциации прямо мотивирован деградацией производительности запросов,
наблюдаемой в продуктивной среде (GitLab Documentation, 2024).

Смежный корпус работ устанавливает, что запросы с множественными соединениями
по своей природе подвержены деградации качества планов. Лейс и др. (Leis et al.,
2015) показали, что ошибки оценки кардинальности накапливаются
мультипликативно при прохождении через цепочку соединений, нередко достигая
нескольких порядков величины даже на хорошо проанализированных таблицах.
Паттерн полиморфного разрешения с его N внешними соединениями подвержен
такому накоплению ошибок.


## Альтернативы на уровне схемы

В литературе по базам данных предложен ряд стратегий моделирования иерархий
типов, позволяющих избежать дискриминированного внешнего ключа. Тиори, Янг и
Фрай предложили систематическую методологию отображения иерархий обобщения
расширенной ER-модели в реляционные таблицы (Teorey et al., 1986). Фаулер
впоследствии каталогизировал три практически ориентированных паттерна: Class
Table Inheritance (общая родительская таблица с таблицами подтипов, первичные
ключи которых являются внешними ключами к родительской), Single Table
Inheritance (все подтипы свёрнуты в одну широкую таблицу) и Concrete Table
Inheritance (полностью независимые таблицы для каждого подтипа, требующие
UNION ALL для полиморфных запросов) (Fowler, 2002). Конкретные компромиссы
стоимости для каждого паттерна рассмотрены в разделе «Практические замечания»
ниже. Общие принципы оптимизации запросов и алгебраические основы внешних
соединений в реляционных СУБД изложены в работе Кузнецова
(Кузнецов С.Д., «Основы современных баз данных»;
https://citforum.ru/database/articles/art_26_1.shtml).

Карвин посвятил отдельную главу книги *SQL Antipatterns* дискриминированному
внешнему ключу под названием «Polymorphic Associations», утверждая, что данный
подход жертвует ссылочной целостностью и производительностью запросов ради
простоты схемы (Karwin, 2010). В качестве предпочтительной альтернативы он
рекомендует подход Class Table Inheritance, который называет «Common
Super-Table».

Несмотря на существование альтернатив, дискриминированный внешний ключ остаётся
доминирующим на практике. ORM-фреймворки генерируют его по умолчанию, а
ретроактивные изменения схемы в крупных продуктивных системах непомерно дороги.
Поэтому оптимизации, описываемые в последующих главах, принимают схему как
данность и нацелены на уровень выполнения запросов.


## Существующие подходы к проблеме производительности

Запрос полиморфного разрешения обходится дорого, потому что исполнитель
зондирует N внутренних таблиц для каждой внешней строки, хотя совпадение может
дать не более чем одна из них. Ряд семейств оптимизаций нацелен на снижение
этой стоимости. В данном разделе приводится обзор релевантных методов и для
каждого из них указывается, почему он не решает проблему полиморфного
паттерна в полной мере.

### Теория внешних соединений

Алгебраические основы оптимизации внешних соединений были заложены Галиндо-
Легарией и Розенталем (Galindo-Legaria and Rosenthal, 1997), разработавшими
правила перезаписи для упрощения и переупорядочения внешних соединений в
рамках реляционной алгебры. Их каркас определяет условия, при которых внешние
соединения могут быть переупорядочены, сгруппированы или преобразованы во
внутренние — что составляет теоретическую основу большинства оптимизаций
внешних соединений в современных планировщиках запросов. В более ранней работе
Галиндо-Легария (Galindo-Legaria, 1994) представил алгебраический каркас на
основе операторов нуллификации, представляющий результат внешнего соединения
как объединение двух непересекающихся компонент: совпавших строк (строк
внутреннего соединения) и несовпавших строк, дополненных NULL-значениями.
Такая декомпозиция позволяет оптимизатору рассуждать о каждой компоненте
отдельно. Для полиморфного паттерна эта декомпозиция особенно эффективна:
взаимное исключение гарантирует, что для каждой строки базовой таблицы не
более чем для одной целевой таблицы компонента внутреннего соединения
непуста (а компонента NULL-дополнения пуста), тогда как для всех остальных
целевых таблиц компонента внутреннего соединения пуста и вклад вносит только
компонента NULL-дополнения. Это означает, что оптимизатор, в принципе, может
определить на уровне отдельной строки, для какого соединения компонента
NULL-дополнения пуста, — более сильный вывод, чем тот, который общий каркас
позволяет сделать без инварианта взаимного исключения.

### Устранение соединений

Если LEFT JOIN доказуемо не нужен — его выходные столбцы не используются и он
не может дублировать строки, — оптимизатор может полностью удалить его.
PostgreSQL поддерживает удаление внешних соединений начиная с версии 9.0 для
случая, когда внутренняя сторона имеет уникальный индекс на ключе соединения
(Haas, 2010; http://rhaas.blogspot.com/2010/06/why-join-removal-is-cool.html).
DB2 и Oracle применяют устранение соединений более агрессивно, используя
метаданные ссылочной целостности для удаления соединений, единственной целью
которых была проверка отношения внешнего ключа
(Pirahesh et al., 1992). Вопросы устранения соединений и механизм их реализации
в PostgreSQL подробно рассматриваются также в книге
(Домбровская Г., Новиков Б., Бейликова А. (2022) «Оптимизация запросов
PostgreSQL». М.: ДМК-Пресс).

Однако в полиморфном паттерне каждое соединение вносит столбец в выражение
COALESCE или CASE. Ни одно из них не подлежит стандартному устранению, поскольку
ссылка на выходной столбец препятствует удалению. Для использования паттерна
необходим более специализированный анализ, который распознаёт ограничение на
использование столбцов и инвариант взаимного исключения совместно.

### Миграция предикатов

Леви, Мамик и Сагив (Levy, Mumick and Sagiv, 1994) разработали технику
перемещения предикатов (predicate move-around), позволяющую выводить новые
предикаты путём миграции существующих между блоками запроса. Применительно к
полиморфному паттерну миграция предикатов могла бы, в принципе, протолкнуть
предикаты дискриминатора из условий соединения вниз, к сканированию базовой
таблицы, ограничив множество строк, достигающих каждого соединения. Однако
перемещение предикатов оперирует предикатами, уже присутствующими в запросе;
потенциал оптимизации полиморфного паттерна состоит в распознавании того,
что целые соединения могут быть пропущены для несовпадающих строк, — это
структурное преобразование, выходящее за рамки миграции предикатов.

### Боковая передача информации

Методы боковой передачи информации (sideways information passing, SIP)
конструируют фильтры на одной стороне соединения и передают их к сканированию
другой стороны. Бансилон и др. (Bancilhon et al., 1986) ввели технику
магических множеств (Magic Sets) для рекурсивных запросов Datalog;
впоследствии техника была адаптирована и обобщена другими исследователями на
реляционную модель как способ распространения связанных значений для ограничения
вычислений при соединении подцелей. Кандула и др. (Kandula et al., 2021)
формализовали современный вариант как *индуцированные данными предикаты* —
синтетические предикаты, выведенные из статистик данных одной таблицы и
применяемые к соединяемой таблице.

Применительно к полиморфному паттерну SIP мог бы распространять значения
дискриминатора из базовой таблицы, чтобы избежать зондирования внутренних
таблиц, чей тип не совпадает. Однако направление потока информации инвертировано
по сравнению с типичным сценарием SIP: полезный фильтр (значение дискриминатора)
находится на внешней стороне, а не на внутренней.

### Переписывание через UNION ALL

Наиболее прямой подход к использованию взаимного исключения — переписать
запрос с N-кратным LEFT JOIN в N отдельных запросов, каждый из которых
ограничен одним значением дискриминатора, и объединить их через UNION ALL:

```sql
SELECT ol.id, p.name AS item_name
FROM order_lines ol
JOIN products p ON ol.item_id = p.id
WHERE ol.item_type = 'product'
UNION ALL
SELECT ol.id, g.name AS item_name
FROM order_lines ol
JOIN gift_cards g ON ol.item_id = g.id
WHERE ol.item_type = 'gift_card'
UNION ALL
SELECT ol.id, s.name AS item_name
FROM order_lines ol
JOIN subscriptions s ON ol.item_id = s.id
WHERE ol.item_type = 'subscription';
```

Каждая ветвь сканирует только релевантное подмножество базовой таблицы и
выполняет внутреннее соединение с единственной целевой таблицей, что исключает
все безрезультатные пробы.

Данное переписывание неявно отбрасывает строки базовой таблицы, значение
дискриминатора которых не покрывается ни одной ветвью. Исходный запрос с LEFT
JOIN сохраняет такие строки с NULL-значениями во всех столбцах целевых таблиц.
Для восстановления семантической эквивалентности необходима замыкающая ветвь:

```sql
UNION ALL
SELECT ol.id, NULL AS item_name
FROM order_lines ol
WHERE ol.item_type NOT IN ('product','gift_card','subscription')
   OR ol.item_type IS NULL;
```

(Предложение `OR ol.item_type IS NULL` необходимо, поскольку `NOT IN`
возвращает NULL, а не TRUE, когда левый операнд равен NULL. Данная формулировка
замыкающей ветви корректна для одноколоночного дискриминатора при условии, что
список констант не содержит NULL, что выполняется в данном случае, так как
значения дискриминатора являются строковыми литералами. Для многоколоночных
дискриминаторов кортежный `NOT IN` обладает более сложной семантикой NULL;
формулировка через `NOT EXISTS` или явную цепочку `IS DISTINCT FROM` является
более безопасной в общем случае.)

При наличии замыкающей ветви переписывание семантически эквивалентно исходному
запросу при выполнении инвариантов взаимного исключения и уникальности ключа,
если каждая пара `(discriminator, item_id)` разрешается в существующую строку
соответствующей целевой таблицы. Если существует «висячая» ссылка — например,
`item_type = 'product'`, но товара с данным `item_id` нет, — то исходный LEFT
JOIN сохраняет строку базовой таблицы с NULL-значениями столбцов целевой
таблицы, тогда как INNER JOIN в ветви переписывания молча отбрасывает её.
В форме полиморфных ассоциаций, лишённой ограничений внешнего ключа, «висячие»
ссылки возможны и это различие существенно. Использование LEFT JOIN вместо
INNER JOIN в каждой ветви сохраняло бы «висячие» ссылки и делало бы
переписывание полностью эквивалентным исходному запросу при тех же затратах
на сканирование базовой таблицы. Данное переписывание является распространённым
практическим обходным решением и естественно соответствует общей стратегии
декомпозиции запроса по значениям предиката с последующим объединением частичных
результатов.

Стоимость этого подхода состоит в том, что он требует N+1 сканирований базовой
таблицы (по одному на каждый целевой тип плюс замыкающая ветвь, или N+1
обращений по индексу при наличии индекса на дискриминаторе), и планировщик
должен оптимизировать N+1 отдельных подзапросов вместо одного. При большом N
накладные расходы на планирование и повторный доступ к базовой таблице могут
перевесить экономию от устранения безрезультатных проб. В последующих главах
исследуются оптимизации, достигающие того же снижения стоимости зондирования
без необходимости многократного сканирования базовой таблицы.

### Адаптивное выполнение запросов

Вместо того чтобы фиксировать единственный план на этапе оптимизации,
адаптивные исполнители откладывают решения на этап выполнения. Грефе
(Graefe, 1994) ввёл мета-оператор `choose-plan`, выбирающий среди
предварительно скомпилированных подпланов на основе условий времени выполнения.
Авнур и Хеллерштейн (Avnur and Hellerstein, 2000) предложили Eddies —
механизм адаптивной маршрутизации отдельных кортежей через операторы. В Oracle
Database 12c адаптивные планы реализованы в промышленной системе: узлы-сборщики
статистики вставляются в план и инициируют переключение подпланов при
расхождении наблюдаемых кардинальностей с оценками
(Oracle Corporation, 2013;
https://www.oracle.com/technetwork/database/bi-datawarehousing/twp-optimizer-with-oracledb-12c-1963236.pdf).

Применительно к полиморфному паттерну адаптивный исполнитель мог бы направлять
каждую внешнюю строку только к соответствующему оператору соединения, пропуская
остальные N−1 проб целиком. Адаптивные соединения Oracle и механизм выбора
соединений SQL Server решают родственную задачу — выбор между вложенным циклом
и хеш-соединением во время выполнения, — однако ни одна существующая
промышленная система не реализует маршрутизацию по значению дискриминатора на
уровне отдельных строк, которая позволила бы полностью пропускать несовпадающие
соединения.

### Исключение по ограничениям

Механизм исключения по ограничениям (constraint exclusion) в PostgreSQL является
ближайшей существующей функциональностью к тому, что требуется для полиморфного
паттерна. При сканировании секционированной таблицы (или представления UNION ALL
над таблицами с CHECK-ограничениями) планировщик сопоставляет предложение WHERE
запроса с CHECK-ограничением каждой дочерней таблицы и исключает дочерние
таблицы, которые заведомо не могут содержать совпадающих строк. Параллель с
полиморфным паттерном прямая: предикаты дискриминатора играют роль
CHECK-ограничений, а целевые таблицы — роль секций. Однако исключение по
ограничениям оперирует дочерними таблицами базовой таблицы, а не внутренними
сторонами LEFT JOIN-ов в несекционированном запросе. Механизм не способен
распознать, что LEFT JOIN к `products` не нужен для строк с
`item_type = 'gift_card'`, если только базовая таблица не секционирована
физически по дискриминатору, — а это, как обсуждалось выше, требует изменений
схемы, которых оптимизации в настоящей работе призваны избежать.

### Ограничение пространства поиска планировщика

Полиморфный паттерн обнажает ограничение не в оценках стоимости планировщика,
а в его пространстве поиска. Планировщик PostgreSQL зачастую способен построить
разумные оценки селективности для каждого предиката дискриминатора на основе
статистики MCV: для соединения вложенным циклом по условию
`ol.item_type = 'product' AND ol.item_id = p.id` планировщик распознаёт, что
совпадения даст лишь та доля строк `order_lines`, где `item_type = 'product'`.
При актуальной статистике оценки кардинальности для каждого отдельного
соединения могут быть вполне адекватными.

Однако планировщик не способен выразить «пропустить это соединение целиком для
строк, где дискриминатор не совпадает». В рамках одного узла вложенного цикла
исполнитель обязан зондировать внутреннюю сторону для каждой внешней строки; он
не может условно обойти зондирование на основе значения дискриминатора. В
результате выполняются N−1 безрезультатных проб на строку. Для соединений
вложенным циклом с индексным зондированием каждая безрезультатная проба включает
обход B-дерева до листовой страницы, сравнение, завершающееся неудачей, и
возврат — реальные затраты ввода-вывода и процессорного времени, накапливающиеся
по N целевым таблицам. Для хеш-соединений стоимость промаха одной пробы ниже
(хеш-поиск, завершающийся неудачей, имеет сложность O(1)), однако совокупные
накладные расходы по N соединениям и множеству строк остаются значительными.
Проблема оптимизации запросов с большим числом соединяемых таблиц, включая
вопросы ограничения `join_collapse_limit` и переключения на алгоритм GEQO,
подробно рассмотрена в статье о работе оптимизатора PostgreSQL
(Habr, 2022; https://habr.com/ru/companies/postgrespro/articles/662021/).

Фундаментальная проблема состоит в том, что структура плана не отражает
инвариант взаимного исключения. Существующее пространство поиска планировщика
не включает форм плана, которые разделяют выполнение по значению дискриминатора
в рамках одного прохода по базовой таблице. Рао и Росс (Rao and Ross, 1998)
показали, как избежать избыточных вычислений в коррелированных подзапросах
путём кеширования и повторного использования промежуточных результатов,
остающихся неизменными между вызовами, — концептуально родственная стратегия,
хотя их работа нацелена на коррелированные подзапросы, а не на внешние
соединения, ограниченные дискриминатором. Оптимизации, представленные в
последующих главах, расширяют пространство поиска планировщика, включая формы
плана, которые используют специфические инварианты полиморфного паттерна.


## Взаимодействие с подзапросами EXISTS

Запрос полиморфного разрешения в представленном выше виде не содержит предложения
WHERE: базовая таблица сканируется целиком и каждая строка проходит через N
LEFT JOIN-ов. Однако на практике запрос часто включает подзапрос EXISTS,
фильтрующий базовую таблицу, — например, ограничивающий строки заказа заказами,
размещёнными в определённом диапазоне дат или принадлежащими конкретному
клиенту:

```sql
SELECT
    ol.id,
    COALESCE(p.name, g.name, s.name) AS item_name
FROM order_lines ol
LEFT JOIN products      p ON ol.item_type = 'product'      AND ol.item_id = p.id
LEFT JOIN gift_cards    g ON ol.item_type = 'gift_card'     AND ol.item_id = g.id
LEFT JOIN subscriptions s ON ol.item_type = 'subscription'  AND ol.item_id = s.id
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.id = ol.order_id
      AND o.placed_at >= '2024-01-01'
);
```

Подзапрос EXISTS в этом примере ссылается только на столбцы внешней (базовой)
таблицы — распространённый на практике случай. Приведённый ниже анализ
предполагает это свойство; подзапрос EXISTS, ссылающийся на столбцы целевых
таблиц, подчинялся бы иным правилам подъёма и здесь не рассматривается.
Способ обработки планировщиком подзапроса EXISTS, относящегося только к базовой
таблице, существенно влияет на производительность, причём результат зависит от
того, преобразуется ли подзапрос в полусоединение, а также от настроек
`join_collapse_limit` и `from_collapse_limit`.

**Случай 1: EXISTS сохраняется как SubPlan (без подъёма).** Когда планировщик
не преобразует EXISTS в полусоединение — например, потому что подзапрос содержит
конструкции, препятствующие подъёму, — он обычно вычисляется как фильтр на
уровне сканирования базовой таблицы или вблизи него (планировщик проталкивает
условие вниз, поскольку оно ссылается только на столбцы базовой таблицы).
Каждая строка `order_lines` проверяется на соответствие SubPlan до попадания в
дерево соединений. Строки, не прошедшие проверку EXISTS, отбрасываются
немедленно, так что до N LEFT JOIN-ов доходят только прошедшие фильтрацию
строки. Это благоприятный случай: фильтр базовой таблицы сокращает веер рано.

**Случай 2: EXISTS преобразуется в полусоединение (в пределах
`join_collapse_limit`).** Планировщик PostgreSQL обычно преобразует простой
подзапрос EXISTS в полусоединение. После подъёма отношение полусоединения
(`orders`) становится одним из базовых отношений, которые планировщик
рассматривает при переборе порядков соединения посредством динамического
программирования (или GEQO). Планировщик вправе рассматривать все допустимые
порядки соединений с учётом ограничений порядка, записанных в структурах
`SpecialJoinInfo` для каждого внешнего и полусоединения. Поскольку предложение
полусоединения ссылается только на столбцы `order_lines`, а LEFT JOIN-ы также
требуют `order_lines` на внешней стороне, планировщик в принципе может
разместить полусоединение рано — выполнив соединение `orders` с `order_lines`
до любого из LEFT JOIN-ов. При точных оценках селективности планировщик, как
правило, выбирает именно такое раннее размещение, и эффект фильтрации
сохраняется. Риск в данном случае состоит не в структурной невозможности
переупорядочения, а в том, что неточные оценки кардинальности (накапливающиеся
по цепочке N соединений, как обсуждалось ранее) могут привести планировщик к
выбору неоптимального порядка, при котором полусоединение размещается позднее
оптимального.

**Случай 3: превышение `join_collapse_limit`.** Запрос полиморфного разрешения
с N целевыми таблицами уже содержит N+1 отношение (базовая таблица плюс N
целевых). Добавление подтянутого полусоединения доводит общее число до N+2.
Когда оно превышает `join_collapse_limit` (по умолчанию 8 в PostgreSQL),
планировщик сохраняет синтаксическую вложенность `JOIN` из парсера вместо
того, чтобы развернуть все отношения в единый список для исчерпывающего
перебора. Ограничение существует потому, что количество порядков соединения
растёт сверхэкспоненциально с числом отношений (Ono and Lohman, 1990), что
делает исчерпывающий поиск непрактичным при умеренно большом числе таблиц.
LEFT JOIN-ы формируют левоглубокое дерево `JoinExpr`, которое планировщик
обрабатывает как единый блок, выполняя соединения в их синтаксическом порядке.
Отношение полусоединения, добавленное в `FromExpr` верхнего уровня при
подъёме, оказывается вне этого вложенного блока. Планировщик не может
вклинить полусоединение в неразвёрнутую цепочку LEFT JOIN — он может лишь
присоединить полусоединение к блоку в целом. В результате полусоединение
вычисляется относительно полного выхода цепочки LEFT JOIN: каждая строка
базовой таблицы проходит через все N LEFT JOIN-ов и лишь затем проверяется
условие EXISTS. Для больших базовых таблиц с селективным предикатом EXISTS
это может ухудшить производительность на порядки по сравнению со случаем 1,
поскольку все N безрезультатных проб на строку выполняются до того, как фильтр
отбросит несовпавшие строки.

Данное взаимодействие усугубляет присущую полиморфному паттерну стоимость.
Запрос с 10 целевыми типами уже содержит 11 отношений; добавление одного
подзапроса EXISTS доводит число до 12, что значительно превышает значение
`join_collapse_limit` по умолчанию. В ERP-системах, где велики как N, так и
число фильтрующих условий, неспособность планировщика вклинить полусоединение
в цепочку LEFT JOIN является повторяющимся источником проблем
производительности. Оптимизации, описанные в последующих главах, должны
учитывать это взаимодействие: уменьшение N за счёт устранения соединений
снижает также общее число отношений, потенциально возвращая его в пределы
`join_collapse_limit` и восстанавливая способность планировщика разместить
полусоединение в выгодной позиции.


## Практические замечания

Наблюдения, приведённые в данном разделе, основаны на практическом опыте и
документации фреймворков, а не на контролируемых экспериментах. Они включены,
поскольку широко встречаются в продуктивных системах и могут помочь
администраторам баз данных и разработчикам распознать и диагностировать паттерн,
однако не должны рассматриваться как строго установленные результаты.

**Распознавание паттерна в выводе EXPLAIN.** Характерным признаком является
цепочка LEFT JOIN-ов, выполняемых методом вложенного цикла, где внутренняя
сторона каждого соединения представляет собой сканирование по индексу различной
таблицы, а фильтр соединения содержит предикат равенства на одном и том же
столбце базовой таблицы (дискриминаторе). В выводе EXPLAIN ANALYZE для каждого
узла вложенного цикла значение «rows removed by join filter» будет близко к
общему числу внешних строк — что подтверждает, что почти каждое зондирование
является безрезультатным. Для хеш-соединений аналогичным индикатором служит
большое количество строк, поступающих в хеш-поиск с нулевым числом совпадений.
Подробные примеры интерпретации EXPLAIN ANALYZE для запросов с множественными
соединениями приведены в
(Домбровская Г., Новиков Б., Бейликова А. (2022) «Оптимизация запросов
PostgreSQL». М.: ДМК-Пресс).

**Компромиссы альтернатив на уровне схемы на практике.** Альтернативы схемы,
описанные ранее (Fowler, 2002; Karwin, 2010), несут конкретные издержки,
влияющие на выбор в продуктивных системах. Class Table Inheritance («Common
Super-Table») сохраняет ссылочную целостность, но добавляет одно соединение на
запрос и требует двух записей на вставку (одна в родительскую таблицу, одна в
таблицу подтипа). Single Table Inheritance полностью избегает соединений, но
порождает широкую разрежённую таблицу — столбцы, принадлежащие другим подтипам,
содержат NULL для данной строки, что может расточать дисковое пространство и
усложнять индексирование. Concrete Table Inheritance исключает как соединения,
так и NULL-значения, но требует UNION ALL по всем таблицам подтипов для
полиморфных запросов, а изменения схемы общих столбцов должны распространяться
на каждую таблицу независимо.

**Обходные решения на уровне ORM.** Документация фреймворков описывает
несколько митигаций на уровне приложения. Библиотека Django `django-polymorphic`
предлагает метод `.non_polymorphic()` для набора запросов, пропускающий
соединения с подтипами, когда конкретный тип не требуется
(django-polymorphic Documentation, 2024;
https://django-polymorphic.readthedocs.io/en/stable/performance.html).
Пользователи Hibernate могут переключиться со стратегии `JOINED` на
`SINGLE_TABLE` ценой разрежённой таблицы, либо использовать ленивую загрузку
для отложенного разрешения подтипов до момента обращения к конкретной сущности —
заменяя N LEFT JOIN-ов в одном запросе на N+1 отдельных запросов, что может быть
как быстрее, так и медленнее в зависимости от шаблонов доступа и кеширования.
В обсуждении на форуме сообщества Hibernate от 2024 года документируется
ситуация, когда разработчики столкнулись с 30–40 LEFT OUTER JOIN-ами из
иерархий умеренной глубины со стратегией `JOINED` и искали именно эти обходные
решения
(https://discourse.hibernate.org/t/is-limiting-the-amount-of-joins-in-the-joined-strategy-possible/9654).

**Когда проблема наиболее ощутима.** Влияние полиморфного паттерна на
производительность наиболее выражено при одновременном выполнении трёх условий:
число целевых типов N велико (более 8–10), базовая таблица велика (миллионы
строк), и запрос является интенсивно читающим с требованиями к времени отклика.
В таких случаях даже индексные пробы вложенного цикла накапливают значительный
объём ввода-вывода: каждая безрезультатная проба обходит B-дерево до листовой
страницы, выполняет сравнение, завершающееся неудачей, и возвращается.
Умноженные на N−1 безрезультатных проб на строку и миллионы строк, совокупные
затраты доминируют во времени выполнения запроса.


## Резюме

Паттерн разрешения полиморфных ссылок порождает запросы с характерным веером
из N левых внешних соединений, линейно растущим с числом целевых типов. Его
структурные инварианты — попарная дизъюнктность предикатов дискриминатора,
уникальность ключа внутренней стороны и ограничение на использование столбцов —
отличают его от произвольных запросов с внешними соединениями и делают возможными
оптимизации, недоступные правилам перезаписи общего назначения. В частности,
инварианты гарантируют, что для любой строки базовой таблицы левые внешние
соединения с несовпадающими целевыми таблицами могут быть удалены без изменения
результата.

Паттерн встречается в двух формах — полиморфные ассоциации (без ссылочной
целостности) и наследование через соединение таблиц (со ссылочной целостностью)
— и повсеместно распространён в схемах, генерируемых ORM, CRM-платформах и
ERP-системах. Практические свидетельства подтверждают, что результирующие запросы
представляют значительную нагрузку на производительность по мере роста N.

Каждый из существующих подходов к оптимизации решает лишь часть проблемы:
устранение соединений требует неиспользуемых выходных столбцов и доказуемого
отсутствия дублирования (Haas, 2010); перезапись внешних соединений предоставляет
алгебраический каркас, но не специфичные для паттерна правила
(Galindo-Legaria and Rosenthal, 1997); миграция предикатов перемещает предикаты,
но не может устранять соединения (Levy et al., 1994); боковая передача информации
распространяет фильтры в неверном для данного паттерна направлении
(Kandula et al., 2021); переписывание через UNION ALL устраняет безрезультатные
пробы, но требует многократного сканирования базовой таблицы; исключение по
ограничениям пропускает секции, но требует физического секционирования базовой
таблицы; адаптивное выполнение могло бы маршрутизировать кортежи построчно,
однако ни одна промышленная система не реализует маршрутизацию на основе
дискриминатора (Graefe, 1994; Oracle Corporation, 2013). Ни один из подходов
не использует полный набор структурных инвариантов в рамках одного прохода по
базовой таблице. Проблема усугубляется подзапросами EXISTS, которые при подъёме
в полусоединения утрачивают фильтрующий эффект на базовую таблицу — в
особенности когда общее число отношений превышает `join_collapse_limit` и
планировщик более не может переупорядочить полусоединение в оптимальную позицию.
Последующие главы описывают серию оптимизаций, специфичных для PostgreSQL,
нацеленных на устранение этого пробела.
