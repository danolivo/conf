# Оптимизация агрегатов PostgreSQL - расширяемый подход

Агрегаты в PostgreSQL не очень-то эффективны. Это особенно заметно в сравнении с SQL Server, когда частичные агрегаты неэффективны - то есть требуется обработать большой поток строк и на выходе получить также большой набор групп и посчитанных по ним агрегатов. Особенно это заметно на типах переменной длины, характерным примером которых является `SUM(numeric)`. Агрегаты построены на том, чтобы обрабатывать значения в общем виде, тогда как на практике значения в базе данных часто ограничены - например, в 1С все numeric имеют фиксированный масштаб.

Отсюда возникает идея соптимизировать агрегаты, подстроив под конкретные условия. Ранее это было возможно сделать только в форке PostgreSQL, Однако совсем недавно, David Rowley добавил в PostgreSQL интересный "хинт" планнера - [prosupport](ссылка на доку постгреса), который позволяет написать расширение, которое во время планирования млжет сделать с агрегатом практически что угодно. А это открывает пространство для интересных технических решений.

Здесь я предлагаю посмотреть, как схема с преобразованием агрегата работает на реальном примере простого расширения для достаточно примитивной трансформации.

В реальных условиях, где запросы генерируются приложением динамически, часто встречаются избыточные конструкции, вроде следующей:

`SUM(x ORDER BY x)`

Действительно, порядок следования значений на сумму не влияет. Так зачем выполнять лишнюю сортировку?
Для начала проверим, действительно ли PostgreSQL сохраняет ненужную операцию сортировки и прикинем, что может дать избавление от неё. Ниже - два запроса с суммированием при наличии сортировки и без нее:

```sql
SELECT sum(x ORDER BY x) FROM
  (SELECT (random()*1E6)::numeric(16,2) AS x FROM generate_series(1,1E7))
OFFSET 1E7;
Time: 4986.870 ms (00:04.987)

SELECT sum(x) FROM
  (SELECT (random()*1E6)::numeric(16,2) AS x FROM generate_series(1,1E7))
OFFSET 1E7;
Time: 3699.393 ms (00:03.699)
```

Значительное ускорение в идеальном случае. Имеет смысл реализовать замену: это будет выполняться один раз на этапе планирования и не должно стоить дорого. А для случая [generic планов](ссылка на доку постгреса) будет ещё и переиспользоваться.

## Заключение

Разрешив трансформацию агрегатной функции, PostgreSQL открыл путь фантазии разработчиков - сделать с агрегатом можно все, что угодно. Это позволит "подчищать" плохо или избыточно сгенерированные запросы, подстраивать агрегаты под конкретные условия эксплуатации СУБД. Здесь мы разобрали простой пример, который просто устраняет неаккуратность генератора запроса. Более сложным примером может служить использование оптимизированной версии SUM(), если на входе numeric известного и небольшого масштаба, см прототип расширения в репозитории на [GitHub](https://github.com/danolivo/pg_numeric_agg_support).
