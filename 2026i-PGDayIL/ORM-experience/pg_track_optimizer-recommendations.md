# pg_track_optimizer: рекомендации по метрикам

Основано на трёх измерениях на нагрузке 1С ERP (стенд 10.200.100.103,
4398 планов auto_explain + 6279 записей расширения):
`pto-detection-quality.md`, `pto-optimization-potential.md` и прогоне
кандидатов `candidates.py` (вывод — `candidates.out`). Все числа ниже —
оттуда. AUC считается против «возвратимого времени», размеченного только
по фактам исполнения; пометка «циклично» значит, что кандидат делит
входные данные с разметкой и его AUC на этой метке цитировать нельзя.

## Сводка

| # | Рекомендация | Сложность | Измеренный эффект |
|---|---|---|---|
| 1 | Починить нормировку `wca` | 1 строка | P@50 0.82 → 0.96 |
| 2 | Убрать `/nnodes` у `twa` | 2 строки | AUC 0.768 → 0.807; на кратности ускорения — лучшая est-метрика (0.808) |
| 3 | Ограничить `lf` формулой доли | ~5 строк | AUC 0.883 → 0.906 + появляется порог |
| 4 | Новая: `umax` — худшая недооценка | ~5 строк | AUC 0.833 на waste от повторов, против 0.814 у `emax` |
| 5 | Новые: три доли возвратимого времени | walker уже всё видит | не оценивается моей разметкой (циклично), аргумент — интерпретируемость |
| 6 | Порог на запись в хеш-таблицу | GUC | −48 % мусорных записей |
| 7 | Второй ключ: хеш формы плана | заметная | лечит развал `queryid` на 1С |
| 8 | Сэмплирование timing | средняя | срезает 35–42 % оверхеда `effort=timing` |

И одно «не делать»: не зашивать время или частоту в хранимые метрики.
Проверено: длительность как признак «можно ускорить в ≥3 раза» даёт AUC
0.550 (монетка), безразмерные метрики — 0.74–0.81. Частота ортогональна
качеству плана (Spearman `avg_avg` ~ calls = +0.006), и её домножение
необратимо портит метрику; `nexecs` и `exec_time` уже есть в представлении
для тех, кому нужен сегодняшний burden.

## 1–2. Правки багов (уже описаны, здесь цифры)

`wca`: нормировать на `Σ total_cost` живых узлов вместо стоимости корня
(`plan_error.c:298`). Сейчас топ метрики — `SELECT 1 FROM pg_temp.tt LIMIT 1`
c `relative_cost` ≈ 68 600. После правки P@50 0.82 → 0.96, доля
возвратимого времени в топ-50 — 0.3 % → 16 %.

`twa`: убрать деление на `nnodes` (`plan_error.c:460`) — веса
`relative_time` уже суммируются в единицу, повторное деление наказывает
большие планы (Spearman отношения `twa/avg` к размеру плана −0.301 до
правки). После: AUC 0.768 → 0.807, а на метке «ускоряется в ≥3 раза» —
0.808, лучший результат среди всех est-vs-actual метрик. После этих двух
правок `wca` всё равно остаётся слабее `twa` по всем меткам (0.741 против
0.808 на кратности) — стоит подумать, нужен ли он вообще, когда `twa`
доступен: единственный его аргумент — работа при `effort=rows`, без
таймингов.

## 3. `lf`/`jf`: доля вместо отношения

Сейчас: `lf = nfiltered/nloops × relative_time / real_rows`, где у
`real_rows` фолбэк `1/nloops`. Деление на почти ноль даёт значения до
9.3 × 10⁶ — метрика без верхней границы, порог к ней не приставить.

Предлагаемая формула:

```
lf = max over scan nodes of  removed / (removed + produced) × relative_time
```

Свойства: ограничена [0, 1]; читается как «доля времени запроса, ушедшая
на строки, выброшенные на этом скане»; `lf > 0.5` — законный порог для
`log_min_error`-подобной фильтрации. Head-to-head на одинаковой метке
(обе цикличны с ней одинаково): 0.906 против 0.883, на «≥3×» — 0.928
против 0.914. То есть ограниченная формула ещё и ранжирует лучше.

`jf` та же правка выравнивает по смыслу, но детекцию не чинит (0.568
против 0.569): его слабость не в формуле, а в том, что на этой нагрузке
джойн-фильтрация редко доминирует. Вариант — слить `lf` и `jf` в одну
метрику «filter waste share» по всем узлам: моя `filt_frac` (сумма по
узлам `self_time × share / total`) даёт ρ = 0.931 с долей возвратимого
времени. Двух колонок (`f_filter_waste` по сканам и джойнам вместе +
отдельно worst node) хватило бы.

## 4. Новая метрика: `umax` — худшая недооценка

Сейчас ошибка берётся по модулю (`plan_error.c:282`), знак выбрасывается.
Но для выбора плана ошибка асимметрична: **недооценка** строк на внешней
стороне ведёт к NestLoop-катастрофе, переоценка — максимум к лишнему
hash. Проверка на нецикличной метке «waste от повторов и проливов»
(построена только на `loops` и признаках пролива, est-метрики её не видят):

| метрика | AUC на waste от повторов |
|---|---:|
| `umax` (худшая недооценка) | **0.833** |
| `uavg` (средняя недооценка) | 0.828 |
| `emax` (худшая ошибка по модулю) | 0.814 |
| `avg_error` | 0.807 |
| `omax` (худшая переоценка, контроль) | 0.737 |

Асимметрия реальна: недооценка предсказывает повторную работу лучше
модуля, переоценка — заметно хуже. Цена — одно сравнение в walker'е.
Замену `avg/rms` она не предлагает (на общей метке `uavg` 0.639 — модуль
нужен, переоценка тоже сигналит, но о другом: о фильтрации). Предлагаю
хранить `umax` как отдельный rstats и в README трактовать: высокий `umax`
→ риск неверной стратегии джойна; высокий `omax` → риск перезаклада
памяти/hash.

## 5. Новые метрики: три доли возвратимого времени

Главная содержательная рекомендация. Метрики ошибок отвечают «оценка
разошлась с фактом», но не «эта ошибка чего-то стоит». Разрыв виден в
данных: `SELECT $1 FROM pg_temp.ttN LIMIT $2` имеет ошибку 5–12 и ноль
возвратимого времени — альтернативного плана не существует. В топе
«коротких, но частых по `avg_error`» таких 10 из 15.

Предлагаю три безразмерных колонки (каждая — rstats по исполнениям,
каждая ∈ [0, 1], сумма — оценка сверху доли возвратимого времени):

```
f_filter_waste = Σ  self_time × removed/(removed+produced)      / total_time
f_repeat_waste = Σ  incl_time × (1 − parent_loops/loops)        / total_time
                    (только по верхним повторяющимся узлам, чтобы не
                     учесть вложенные повторы дважды)
f_spill_waste  = Σ  self_time × k                               / total_time
                    k = 0.5 при external sort, 0.3 при Batches > 1
```

Всё, кроме проливов, walker уже читает: `nfiltered1/2`, `ntuples`,
`nloops`, per-node timing. Проливы требуют заглянуть в
`SortState`/`HashState`, как это делает `explain.c` — работает только при
`effort=timing`, что согласуется с текущей моделью уровней.

Честная оговорка: моя разметка потенциала построена из этих же величин,
поэтому AUC «доли» на ней цитировать нельзя (0.998 — тавтология).
Аргументы за неё другие: во-первых, каждое слагаемое сразу называет
лечение (индекс/pushdown; стратегия джойна/материализация; `work_mem`) —
это диагноз, а не флаг; во-вторых, она безразмерна и
частотно-независима — ровно та семантика «потенциала», которую
расширение обещает; в-третьих, `rec_frac ≥ 0.667` буквально читается как
«запрос можно ускорить втрое». Проверить её надёжность нужно не на моей
разметке, а реплеем (см. финал).

## 6. Порог на запись

48 % записей на стенде — планы ≤ 2 узлов с нулевой ошибкой и временем
~0.01 мс, суммарно 4.7 % времени. Они съедают `hash_mem`, а по исчерпании
бюджета новые запросы молча теряются. GUC вида `track_min_nodes = 3` или
`track_min_error > 0` при `mode=forced` (с текущими дефолтами поведение
не меняется). Дёшево и удваивает полезную ёмкость таблицы.

## 7. Ключ агрегации: `queryid` разваливается на 1С

Имена временных таблиц входят в текст запроса → `tt833` и `tt834` дают
разные `queryid`. Следствия: медиана `nexecs` = 1, running-статистики
вырождаются в единичные наблюдения (`min == max` у 88 % записей),
детектор нестабильности планов через `njoins` нашёл 1 запрос из 6279.
Это не экзотика: так работает любой ORM с генерируемыми временными
таблицами.

Варианты по возрастанию сложности: нормализовать имена `pg_temp.*` при
вычислении собственного ключа; или добавить второй ключ — хеш формы плана
(jumble по типам узлов и постоянным relid'ам), который заодно делает
детектор нестабильности планов честным: один текст → разные формы = смена
плана, разные тексты → одна форма = одна рабочая точка. Второй вариант
интереснее и как отдельная фича: сравнение статистик «по форме плана»
между `queryid` — это то, чего нет ни у кого из соседей по нише.

## 8. Сэмплирование timing

Лучшие метрики (`twa`, `lf`, предлагаемые доли) живут только при
`effort=timing`, а это 35–42 % оверхеда на tuple-heavy сканах
(`benchmarking.md`). GUC `timing_sample_rate` (доля исполнений с
таймингом; остальные идут по ветке `effort=rows`) снял бы конфликт
«полезность против цены» — rstats по построению нормально переживают
разное число наблюдений в разных колонках. Дефолт 1.0 — поведение не
меняется.

## Приоритет внедрения

Правки 1–3 — до любого следующего замера, они меняют сами измеряемые
величины и стоят часы. Затем 6 (порог) — бесплатная гигиена. Затем 4
(`umax`) как самая дешёвая новая метрика с нецикличным измеренным
выигрышем. Доли (5) и хеш формы плана (7) — самые ценные и самые дорогие;
их стоит проектировать вместе, потому что доли без стабильного ключа
агрегации на ORM-нагрузках будут так же вырождаться в единичные
наблюдения.

## Как проверить не на моей разметке

Реплей на стенде: взять топ-30 по `twa_fix`, топ-30 по `rec_frac` и
топ-30 по времени (контроль), прогнать каждый в матрице {`ANALYZE`,
`work_mem × 8`, `enable_nestloop = off`, индекс-кандидат по худшему
скану} и считать фактическое ускорение. Precision метрики = доля её
топа, где хоть одна ячейка матрицы дала ≥ 2×. Инфраструктура есть
(`1c-lab/14-replay-ab.sh`, `synthetic/extract_replayable.py`);
ограничение — воспроизводимы только запросы к постоянным таблицам, 1С-шные
`pg_temp.tt*` уже не существуют.
