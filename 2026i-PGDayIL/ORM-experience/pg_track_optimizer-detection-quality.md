# Находят ли метрики pg_track_optimizer плохие запросы?

Данные: 1С-стенд `10.200.100.103`, кластер `1C_18_1-decimal128`, БД `erp_v`,
нагрузка 1С 13–17 августа 2026. `pg_track_optimizer` 0.9.3 в режиме
`mode=forced`, `effort=timing`. Снимок от 2026-08-20.

Скрипты: `pto_eval.py` (основные метрики качества), `pto_eval2.py`
(диагностика). Оба на чистом stdlib, запускаются из каталога с
`1c-explains/*.csv`.

## Метод

«Истина» берётся из `pg_stat_statements` — независимого инструмента, чтобы
проверка не выродилась в тавтологию:

| Метка | Определение | Позитивов |
|---|---|---:|
| `slow/call` | верхние 10 % по `mean_exec_time` (≥ 329 мс) | 627 |
| `heavy_tot` | верхние 10 % по `total_exec_time` (≥ 416 мс) | 627 |
| `temp` | `temp_blks > 0` | 14 |
| `ineffic` | верхние 10 % по мс на блок | 627 |

Качество детекции — ROC AUC (0.5 = монетка), precision@50 (какая доля
топ-50 по метрике действительно медленная) и доля общего
`total_exec_time`, попавшая в топ-K («burden»).

Соединение по `queryid` дало 6279 из 6279 записей — 100 %, `time_avg`
против `mean_exec_time` даёт AUC 1.000, то есть джойн корректен.
`pg_stat_statements` при этом знает 17 663 запроса: расширение видит
чуть больше трети.

## Короткий ответ

**Семейство логарифмических ошибок оценки (`avg`, `rms`, `twa`, `wca`) на
этой нагрузке практически не находит проблемных запросов.** Оно исправно
находит ошибки кардинальности — но в 1С ошибки кардинальности сидят в
безобидных запросах к пустым временным таблицам, а не там, где горит время.

Полезны две вещи: `lf` (фильтрация в листьях) и `jf` (фильтрация в
джойнах). Они не столько «находят» медленные запросы — те и так видны по
времени — сколько **объясняют, почему** запрос медленный.

Практический вывод: сначала отбирай по влиянию, потом ранжируй по ошибке.

## Что нашлось в коде

### 1. `wca_error` не нормирован — топ полностью занят `LIMIT` и `MIN()`

`plan_error.c:298`: `relative_cost = pstate->plan->total_cost / ctx->totalcost`,
где `totalcost` — стоимость корневого узла. Предполагается, что доля ≤ 1,
но это неверно, когда корень дешевле поддерева: `LIMIT` планируется на
малую долю строк, а `InitPlan` под `Result` в стоимость корня не входит
вовсе. Отношение тогда улетает на несколько порядков.

Факты: `wca_avg > 30` (потолок правдоподобной логарифмической ошибки) у
985 запросов (15.7 %), `> 10⁶` — у 84. Из топ-200 по `wca_avg`
**все 200** содержат `LIMIT`, `MIN()` или `MAX()`. Максимум — 3.4 · 10⁷ на
`SELECT MIN(T1._Period) FROM _AccumRg50125 ...`, которая исполняется 13 мс.
Метрика в текущем виде не измеряет то, что заявлено, и это объясняет её
худший результат во всех таблицах.

План из логов стенда — ровно этот случай:

```
Query Text: SELECT 1 FROM pg_temp.tt143 LIMIT 1
Limit  (cost=0.13..0.19 rows=1 width=4) (actual time=1405.055..1405.058 rows=1.00 loops=1)
  ->  Seq Scan on pg_temp.tt143  (cost=0.00..13043.51 rows=208251 width=4)
                                 (actual time=1405.053..1405.054 rows=1.00 loops=1)
```

`relative_cost` для узла Seq Scan = 13043.51 / 0.19 ≈ 68 600, ошибка узла
= |ln(1 / 208251)| ≈ 12.2, дальше делим на два узла — и получаем ту самую
величину порядка 10⁵…10⁷.

Нормировать стоит на сумму `total_cost` по всем узлам либо на
`max(root.total_cost, Σ поддеревьев)`.

### 2. Двойная нормировка `twa` и `wca`

`plan_error.c:460,463`: `twa_error` и `wca_error` делятся на `nnodes`,
хотя их веса (`relative_time`, `relative_cost`) уже суммируются в единицу.
Получается взвешенное среднее, ещё раз поделённое на размер плана, — то
есть метрика систематически занижается тем сильнее, чем крупнее план.
Именно противоположное заявленной в README цели «сравнивать запросы разной
структуры».

Проверка на данных: `wca_avg / avg_avg` против `plan_nodes` даёт
Spearman **−0.771**, `twa_avg / avg_avg` — **−0.301**. Для сравнения,
`rms_avg / avg_avg` даёт +0.556 (ожидаемо: RMS растёт с разбросом ошибок).
Лечится удалением двух строк.

### 3. `lf` и `jf` неограниченны из-за фолбэка `real_rows`

`plan_error.c:279`: если все строки отфильтрованы, `real_rows` заменяется
на `1/nloops`. Дальше `lf_factor = nfiltered1/nloops × relative_time /
real_rows`, то есть деление на почти ноль. Отсюда значения вида 9.3 · 10⁶.
Ранжирование при этом остаётся осмысленным (топ `lf` — настоящие тяжёлые
`INSERT ... SELECT`, P@50 = 0.92), но абсолютного порога у метрики нет:
документировать её надо как рейтинг, а не как величину, к которой
применимо `WHERE lf_avg > X`.

### 4. Половина записей — мусор, занимающий `hash_mem`

У 3030 записей из 6279 (48 %) `avg_error = 0`: медиана 2 узла плана,
медианное время 0.01 мс, суммарно 4.7 % общего времени. Это `SELECT $1
FROM pg_temp.ttNNN LIMIT $2` и подобное. При `hash_mem = 2 GB` это пока не
проблема, но на живой базе бюджет будет съеден именно ими, а по достижении
лимита новые запросы молча игнорируются. Просится порог: не хранить
запись, если план ≤ 2 узлов и ошибка нулевая, либо если `exec_time`
меньше заданного минимума.

### 5. Детектор нестабильности планов на 1С не работает

`njoins.min != njoins.max` нашлось ровно у **одного** запроса из 6279.
Причина не в планировщике, а в 1С: имя временной таблицы входит в текст
запроса (`tt833`, `tt1153`, …), поэтому каждое исполнение получает
собственный `queryid`. Медиана `nexecs` = 1, а `min == max` у 87.8 %
записей (среди `nexecs ≥ 5` — у 55.9 %). Любая накопительная статистика
по `queryid` на такой нагрузке обесценивается; для 1С полезнее была бы
нормализация имён временных таблиц или группировка по структуре плана.

## Что делать

1. Починить нормировку `wca` (пункт 1) и убрать двойное деление на
   `nnodes` (пункт 2) — после этого проверку стоит повторить, эти две
   метрики сейчас оценены заведомо в худшем виде, чем задумано.
2. Не позиционировать метрики ошибок как самостоятельный детектор.
   Рабочий сценарий: отбор по влиянию (`time_avg`, `blks_avg`, `nexecs`),
   затем ранжирование по `rms`/`jf`/`lf` — что именно чинить в отобранном.
3. Добавить в README честную оговорку: высокая ошибка кардинальности на
   пустых временных таблицах — норма и не требует действий. Иначе первый
   же пользователь на 1С получит топ из безобидных `LIMIT`-запросов.
4. `jf` и `lf` — самое ценное, что есть в расширении, и они собираются
   только при `effort = timing`. Стоит вынести это в README явно.
5. Порог на запись (пункт 4) и, для 1С-подобных нагрузок, что-то вместо
   `queryid` (пункт 5).

## Ограничения этой проверки

- Одна нагрузка, одна база. Это 1С ERP с массовым созданием временных
  таблиц — не худший, но и совсем не типичный OLTP.
- «Плохой запрос» здесь = медленный или прожорливый. Запрос может быть
  медленным при идеальном плане, и наоборот; прямой разметки «план плохой,
  и его можно улучшить» у нас нет. Поэтому низкий AUC метрики ошибок —
  это не доказательство её бесполезности, а доказательство того, что на
  этой нагрузке ошибки оценки и реальная боль почти не пересекаются.
- Счётчики `pg_stat_statements` и `pg_track_optimizer` накопительные и
  покрывают несколько прогонов, а не один; сравнение идёт на уровне
  агрегатов за всё время жизни кластера.
- `temp_spill` дала всего 14 позитивов — выводы по колонке `temp`
  статистически пустые.
