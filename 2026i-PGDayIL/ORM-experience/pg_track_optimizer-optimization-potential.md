# pg_track_optimizer против потенциала оптимизации

Продолжение `pto-detection-quality.md` с исправленной постановкой задачи.
Предыдущая проверка спрашивала «находит ли расширение медленные запросы» —
это не то, для чего оно сделано. Правильный вопрос: **находит ли оно
запросы, у которых есть хороший потенциал для оптимизации.**

Скрипт: `potential.py` (чистый stdlib, запускается на стенде).

## Как измерен потенциал

Разметка строится **только из фактов исполнения** — сколько строк узел
вернул, сколько выбросил фильтром, сколько раз был перезапущен, сколько
времени потратил. Планировочные оценки в разметку не входят вообще,
поэтому она не циклична с метриками ошибок, которые как раз и живут на
сравнении оценки с фактом.

«Возвратимое время» одного исполнения складывается из трёх слагаемых:

| Слагаемое | Формула | Что можно сделать |
|---|---|---|
| Фильтрация | `self_time × removed / (removed + produced)` по скан- и джойн-узлам | индекс, pushdown предиката |
| Повторы | `inclusive_time × (1 − parent_loops / loops)` на самом верхнем повторяющемся узле | hash/merge вместо NestLoop, материализация SubPlan |
| Проливы | `0.5 × self_time` при external sort, `0.3 × self_time` при `Batches > 1` | `work_mem` |

Сумма обрезается по фактической длительности исполнения. Это **оценка
сверху**: индекс не делает скан бесплатным, а hash join тоже стоит денег.
Как относительная шкала для ранжирования этого достаточно, как обещание
секунд — нет.

Разобрано 4398 планов из 4403 блоков логов 13–17 августа. Все они прошли
порог `auto_explain.log_min_duration = 100`, то есть выборка — это уже
только те исполнения, которые в принципе стоит оптимизировать. Медиана
2.3 с, максимум 4 720 с (одно исполнение 1С-расчёта себестоимости, 79
минут). Время корня плана совпадает с залогированной длительностью в
пределах 25 % у 97.4 % планов — парсер читает планы правильно.

Итог по выборке:

| | секунды | доля залогированного времени |
|---|---:|---:|
| всего в этих исполнениях | 84 478 | 100 % |
| возвратимо (оценка сверху) | 41 537 | **49.2 %** |
| — фильтрация | 31 524 | 37.3 % |
| — повторы | 10 249 | 12.1 % |
| — проливы | 2 579 | 3.1 % |

Метка «есть потенциал» = возвратимо ≥ 100 мс **и** ≥ 30 % своего времени:
1657 исполнений из 4398 (37.7 %), в них 97.6 % всего возвратимого времени.

## Главный результат

Метрики пересчитаны из тех же планов ровно так, как их считает
`plan_error.c`, плюс два починенных варианта и один предложенный.

| ранжирование | AUC | ρ(возвр. мс) | P@50 | rec@20 | rec@50 | rec@200 |
|---|---:|---:|---:|---:|---:|---:|
| `avg_error` | **0.807** | 0.640 | 0.94 | 0.0 % | 2.3 % | 27.9 % |
| `rms_error` | 0.805 | 0.646 | 0.80 | 0.7 % | 1.6 % | 27.3 % |
| худшая ошибка узла | 0.799 | 0.654 | 0.78 | 12.3 % | 15.2 % | 26.3 % |
| `twa` как реализовано | 0.768 | 0.509 | 0.74 | 0.0 % | 0.3 % | 1.7 % |
| `twa` без `/nnodes` | **0.807** | 0.601 | 0.98 | 1.3 % | 2.6 % | 23.6 % |
| `wca` как реализовано | 0.778 | 0.576 | 0.82 | 0.1 % | 0.3 % | 8.1 % |
| `wca` с нормировкой на Σcost | 0.787 | 0.607 | 0.96 | 0.7 % | 16.0 % | 32.9 % |
| `lf` (фильтр в листьях) | 0.883¹ | 0.760 | 1.00 | 11.0 % | 15.4 % | 17.0 % |
| `jf` (фильтр в джойнах) | 0.569 | 0.293 | 0.98 | 5.7 % | 9.1 % | 20.4 % |
| `sp` (фактор SubPlan) | 0.694 | 0.532 | 0.96 | 2.0 % | 16.6 % | 28.2 % |
| **`Σ ошибка × время узла`** | 0.785 | **0.686** | 0.98 | **29.8 %** | **44.6 %** | 72.1 % |
| длительность (базовая линия) | 0.625 | 0.510 | **0.36** | 22.9 % | 29.4 % | 72.8 % |
| случайный выбор | 0.500 | 0.000 | 0.38 | 0.5 % | 1.1 % | 4.5 % |

`rec@K` — какая доля всего возвратимого времени попадает в топ-K этого
ранжирования. ¹`lf` частично циклична с разметкой: обе построены на числе
отфильтрованных строк.

**Тезис расширения подтверждается.** Ошибка оценки кардинальности —
хороший признак потенциала: AUC 0.807 против 0.625 у простой сортировки по
длительности, precision@50 0.94 против 0.36. То есть из 50 запросов,
которые `avg_error` ставит наверх, 47 действительно имеют существенное
возвратимое время, а из 50 самых долгих — только 18. Отсортировать по
времени, как это делает `pg_stat_statements`, здесь **хуже**, чем
отсортировать по ошибке оценки. Это ровно та ниша, на которую расширение
претендует, и она реальна.

## Проверка на цикличность

Разметку можно разложить на части. «Только фильтрация» делит входные
данные с `lf`/`jf` — там они в выигрышном положении. А вот «повторы +
проливы» построены исключительно на `loops` и признаках пролива, то есть
на том, чего метрики ошибок вообще не видят:

| ранжирование | вся разметка | только фильтрация | повторы + проливы |
|---|---:|---:|---:|
| позитивов | 1657 | 1327 | 496 |
| `avg_error` | 0.807 | 0.762 | **0.807** |
| `rms_error` | 0.805 | 0.755 | **0.811** |
| худшая ошибка узла | 0.799 | 0.741 | 0.814 |
| `wca` с нормировкой | 0.787 | 0.744 | 0.784 |
| `lf` | 0.883 | 0.910 | 0.640 |
| `sp` | 0.694 | 0.579 | **0.937** |
| длительность | 0.625 | 0.587 | 0.671 |

Самый честный результат таблицы: **ошибка оценки предсказывает waste от
повторов с AUC 0.81, хотя ничего о повторах не знает.** Механизм ровно
тот, на который расширение и рассчитано: недооценка строк на внешней
стороне → NestLoop вместо hash join → внутренняя ветка исполняется тысячи
раз. Здесь метрика работает как причинный индикатор, а не как корреляция.

`sp` на этой метке даёт 0.937 — но он и построен на `loops`, так что это
скорее проверка того, что моя разметка и его формула согласованы.

Отдельно — без однонодовых планов (защита от артефакта «простой скан с
фильтром»): n = 3332, `avg_error` 0.740, `lf` 0.850, длительность 0.563.
Сигнал слабее, но порядок сохраняется.

## Что это меняет в предыдущем отчёте

Сохраняется полностью:

1. **`wca_error` сломан.** Топ по нему — `SELECT 1 FROM pg_temp.tt143
   LIMIT 1`: 1405 мс, возвратимого времени 0. Из-за деления на стоимость
   корня. Правильная нормировка (на сумму `total_cost` узлов) поднимает
   P@50 с 0.82 до 0.96, а `rec@50` — с 0.3 % до 16.0 %, то есть в пятьдесят
   раз, от правки в одну строку.
2. **Двойная нормировка `twa`.** Убрать `/nnodes`: AUC 0.768 → 0.807,
   P@50 0.74 → 0.98, `rec@200` 1.7 % → 23.6 %.
3. **48 % записей — пустышки** с нулевой ошибкой и планом из двух узлов.
4. **На 1С `queryid` разваливается** из-за имён временных таблиц, поэтому
   накопительная статистика и детектор нестабильности планов не работают.

Отменяется: вывод «метрики ошибок бесполезны». Он был получен на метке
«медленный запрос», а на метке «есть что оптимизировать» те же метрики
уверенно обыгрывают сортировку по времени. Мой предыдущий отчёт мерил не
то, что заявляет расширение.

Уточняется: **метрики годятся как классификатор, но не как приоритизатор.**
Они безразмерны и не отличают запрос на 1.2 с от запроса на 79 минут:
`avg_error` при P@50 = 0.94 захватывает всего 2.3 % возвратимого времени в
топ-50. Умножение на время (`Σ ошибка_узла × self_time` узла) даёт 44.6 %
против 29.4 % у сортировки по длительности и 1.1 % у случайного выбора —
и это, пожалуй, главная практическая находка: **у расширения уже есть все
входные данные, чтобы отдавать оценку возвратимых миллисекунд, а не
безразмерный рейтинг.**

## Безразмерность — это не баг, а требование

Возражение: короткий запрос завтра может исполняться миллион раз в час, и
его ускорение в десять раз окажется важнее большого разового запроса.
Значит метрика обязана быть безразмерной, а домножать на текущее время —
значит зашивать в неё сегодняшнюю нагрузку. Проверил, и данные это
подтверждают (скрипт `pto_freq.py`).

**Метрики предсказывают кратность ускорения, а не только миллисекунды.**
Целевая величина — `возвратимое / длительность`, то есть во сколько раз
запрос мог бы стать быстрее: 0.667 → 3×, 0.9 → 10×. Таких исполнений
1101 и 904 из 4398 соответственно.

| метрика | ρ(возвр. мс) | ρ(доля) | AUC ≥ 3× | AUC ≥ 10× |
|---|---:|---:|---:|---:|
| `avg_error` | 0.640 | 0.640 | 0.774 | 0.744 |
| `rms_error` | 0.646 | 0.638 | 0.766 | 0.735 |
| `twa` без `/nnodes` | 0.601 | **0.646** | **0.808** | **0.804** |
| `wca` с нормировкой | 0.607 | 0.595 | 0.741 | 0.708 |
| `lf` | 0.760 | 0.843 | 0.914 | 0.934 |
| `Σ ошибка × время` | 0.686 | 0.599 | 0.742 | 0.730 |
| длительность | 0.510 | **0.273** | **0.550** | 0.542 |

Длительность как признак кратности ускорения почти бесполезна (0.550), а
безразмерные метрики держат 0.74–0.81. То есть на вопрос «какой запрос
можно ускорить в разы» отвечают именно они, и никакой `pg_stat_statements`
их не заменит.

**На коротких исполнениях метрики работают лучше, а не хуже.** Ровно тот
случай, о котором речь: запрос сейчас дешёвый, но завтра может стать
горячим.

| полоса длительности | n | с потенциалом ≥ 3× | AUC `avg` | AUC `lf` | AUC длительности |
|---|---:|---:|---:|---:|---:|
| 100–300 мс | 500 | 9.0 % | **0.869** | 0.945 | 0.558 |
| 300–1000 мс | 631 | 37.6 % | 0.818 | 0.929 | 0.364 |
| > 1000 мс | 3267 | 25.1 % | 0.754 | 0.903 | 0.573 |

**Метрика ортогональна частоте.** Spearman `avg_avg` против числа вызовов
= **+0.006**, против среднего времени = +0.317. То есть она измеряет
качество плана, а не сегодняшний трафик — как и задумано. Ранжирование,
куда домножена частота, эту информацию необратимо теряет: из «топа по
времени» нельзя восстановить, какой из запросов станет горячим завтра.

**Покрытие — отдельный аргумент в пользу такого дизайна.** 190 запросов
исполнялись 100 и более раз, и **ни один** не дотягивает до
`auto_explain.log_min_duration = 100`. Запросов со средним временем меньше
100 мс — 86.3 % (5419 из 6279). Всё это `auto_explain` не видит вообще, а
`pg_track_optimizer` в режиме `forced` видит. Пример из списка: `SELECT
T1._Period, T1._RecorderTRef, ... FROM _AccumRg...` — 0.39 мс, 1824
вызова, `avg_avg` = 8.58, то есть оценка расходится с фактом примерно в
5000 раз. Сегодня это 0.7 с суммарно и никого не волнует; при росте
частоты на три порядка это первый кандидат в инциденты.

Оговорка ради полноты: в *этой* нагрузке короткие запросы держат лишь
4.4 % общего времени, и из топ-100 по суммарному времени только 3 имеют
среднее меньше 100 мс. Так что аргумент про частоту здесь пока
гипотетический — но именно поэтому хранить надо частотно-независимую
величину: сегодняшняя частота не предсказывает завтрашнюю.

**Что из моей критики остаётся.** Не масштаб, а другое: метрики измеряют
**ошибку оценки, а не субоптимальность плана**, а расходятся эти две вещи
там, где ошибка не меняет выбор плана. `SELECT $1 FROM pg_temp.ttN LIMIT
$2` даёт ошибку 5–12 при нулевом возвратимом времени: альтернативного
плана просто нет. В списке «спящих гигантов» (короткие, но частые, по
`avg_error`) 10 из 15 верхних — именно такие запросы. Лечится это не
домножением на время, а безразмерной же величиной — долей возвратимого
времени: `twa` без `/nnodes` даёт по кратности ускорения 0.808 против
0.774 у `avg_error`, потому что время в нём уже учтено как вес, а не как
множитель.

Поэтому предложение №2 ниже стоит читать так: нужна не абсолютная шкала
вместо безразмерной, а **безразмерная оценка кратности** (доля возвратимого
времени) рядом с ошибкой оценки. Абсолютные миллисекунды на исполнение
пусть тоже будут — но как отдельная колонка, чтобы пользователь сам
домножал на свою ожидаемую частоту, а не получал её зашитой в рейтинг.

## Предложения

1. Починить `wca` (нормировка) и `twa` (лишнее `/nnodes`) — они сейчас
   оценены хуже, чем задумано, и обе правки тривиальны.
2. Добавить оценку возвратимого времени по трём слагаемым из этого отчёта
   (входные данные уже собираются: `nfiltered1/2`, `nloops`, per-node
   timing) — **и как долю от длительности исполнения** (кратность
   ускорения, частотно-независимая), и как абсолютные миллисекунды на
   исполнение. Домножение на частоту оставить пользователю: `nexecs` в
   представлении уже есть.
3. В README развести две задачи: «где ошибка оценки» (это `avg`/`rms`) и
   «где ошибка оценки стоит денег» (это оценка возвратимого времени).
   Пользователь на 1С без второго получает топ из безобидных запросов.
4. `jf` слаб (AUC 0.569) — стоит посмотреть на формулу отдельно: скорее
   всего мешает деление на `real_rows` с фолбэком `1/nloops`.

## Ограничения и что мерить дальше

Разметка — это оценка по плану, а не измерение. Она говорит «здесь время
тратится на выброшенные строки и на повторы», но не доказывает, что
существует план, который этого избежит.

Настоящее измерение — воспроизведение: взять топ-N по каждой метрике и
прогнать каждый запрос в нескольких конфигурациях (`work_mem` ×8,
`enable_nestloop = off`, добавленный индекс-кандидат, свежий `ANALYZE`),
измерить фактическое ускорение, и уже по нему считать precision каждой
метрики. Инфраструктура для этого на стенде есть
(`1c-lab/14-replay-ab.sh`, `synthetic/extract_replayable.py`). Ограничение:
временные таблицы 1С уже не существуют, поэтому напрямую воспроизводимы
только запросы к постоянным таблицам (`_AccumRg*`, `_Document*`, `_Reference*`) —
это меньшая часть тяжёлых исполнений, но достаточная, чтобы получить
честные числа.
