# Эксперимент: numeric с 4-байтовым заголовком вместо упакованного

Проверка гипотезы: если хранить `numeric` всегда с полным 4-байтовым varlena-заголовком
и выравниванием, `pg_detoast_datum()` перестанет делать `palloc` + `memcpy` на каждый
вызов функции. Что мы за это заплатим и что получим?

## Стенд

| | |
|---|---|
| PostgreSQL | 18.4, aarch64-linux (сборка `@embedded-postgres/linux-arm64`) |
| Железо | 4 vCPU, 3 GB RAM, VM на Apple silicon |
| Конфиг | `shared_buffers=900MB`, `jit=off`, `max_parallel_workers_per_gather=0`, `fsync=off`, `autovacuum=off` |
| Данные | 5 000 000 строк, `(id int, x numeric(11,4), y numeric(11,4))` |
| Значения | `round(random()*999999, 4)` — до 1e6, 4 знака после запятой, 3 `NumericDigit` |

Две таблицы с идентичными данными (проверено `EXCEPT ALL` → 0 расхождений),
различие только в `attstorage` колонок `x`, `y`:

```sql
ALTER TABLE t_plain ALTER COLUMN x SET STORAGE PLAIN;
```

---

## Ловушка №1: `INSERT` игнорирует `attstorage`, `COPY` — нет

Первая попытка загрузить `t_plain` обычным `INSERT` дала таблицу, **побайтно совпадающую**
с упакованной. Причина в `fill_val()` (`src/backend/access/common/heaptuple.c`):

```c
else if (VARATT_IS_SHORT(val))
{
    /* no alignment for short varlenas */
    data_length = VARSIZE_SHORT(val);
    memcpy(data, val, data_length);          /* <- attstorage вообще не смотрим */
}
else if (att->attispackable && VARATT_CAN_MAKE_SHORT(val))
{
    /* convert to short varlena -- no alignment */
    ...
}
```

Если входной datum **уже** короткий, он копируется как есть — ветка с `attispackable`
недостижима. При `INSERT ... SELECT` из другой таблицы значение приходит именно таким.

Но и `INSERT ... VALUES` с литералом (свежий 4-байтовый datum) тоже дал короткий заголовок.
Здесь виноват другой механизм — `ExecGetInsertNewTuple()`
(`src/backend/executor/nodeModifyTable.c`):

```c
if (newProj == NULL)
{
    if (relinfo->ri_newTupleSlot->tts_ops != planSlot->tts_ops) { ... }
    else
        return planSlot;        /* дескриптор плана, а не отношения */
}
```

Дескриптор плана строится через `TupleDescInitEntry()`, где
`att->attstorage = typeForm->typstorage` — то есть берётся `typstorage` **типа**
(`m` для numeric), а не `attstorage` **колонки**. `COPY` же формирует кортеж
по `RelationGetDescr(cstate->rel)` и `attstorage` уважает.

Проверка на четырёх вариантах:

| таблица | attstorage | `INSERT VALUES` | `COPY` |
|---|---|---|---|
| `text` | `p` (plain) | 1B short | **4B full** |
| `text` | `x` (extended) | 1B short | 1B short |
| `numeric` | `p` (plain) | 1B short | **4B full** |
| `numeric` | `e` (external) | 1B short | 1B short |
| `numeric` | `m` (main) | 1B short | 1B short |

**Вывод: `SET STORAGE PLAIN` влияет на упаковку заголовка только при загрузке через `COPY`.**
Документированное поведение `attstorage` (сжатие / вынос в TOAST) от этого не страдает —
оно применяется позже, в `heap_toast_insert_or_update()`, по дескриптору отношения.
Протекает наружу только решение об упаковке короткого заголовка.

## Цена в байтах

Загрузка через `COPY`, обе таблицы `VACUUM (ANALYZE, FREEZE)`:

| | t_packed | t_plain | дельта |
|---|---|---|---|
| первый байт атрибута `x` | `0x13` → 1B short | `0x30` → 4B full | |
| длина атрибута | 9 байт | 12 байт | +3 |
| средняя длина кортежа | 45.96 | 51.98 | +6 |
| кортежей на страницу | 157 | 136 | −13.4 % |
| страниц | 31 856 | 36 800 | +15.5 % |

Сырое значение `123456.7890`:
`13 01 82 5300 3f06 8811` (short) против `30000000 01 82 5300 3f06 8811` (full).

## Warm cache: всё в `shared_buffers`

Обе таблицы через `pg_prewarm`, `EXPLAIN` подтверждает `shared hit`, промахов нет.
15 повторов, случайный порядок, медиана / минимум.

| запрос | detoast/строку | packed, мс | plain, мс | дельта | экономия на detoast |
|---|---|---|---|---|---|
| `count(*)` | 0 | 93.0 / 92.1 | 95.3 / 93.3 | **+1.3 %** | — |
| `sum(x)` | 1 | 208.3 / 203.8 | 155.3 / 152.9 | **−25.0 %** | 10.2 нс |
| `count(*) WHERE x>500000` | 1 | 241.3 / 226.3 | 183.5 / 168.1 | **−25.7 %** | 11.6 нс |
| `sum(x+y)` | 2 | 412.9 / 406.3 | 383.4 / 377.5 | −7.1 % | 2.9 нс |
| `sum(x*y+x)` | 3 | 550.0 / 538.9 | 495.4 / 481.9 | −10.6 % | 3.8 нс |
| `sum(x+y+x+y)` | 4 | 744.5 / 730.3 | 685.4 / 671.1 | −8.1 % | 3.0 нс |

Контроль без клиентского round-trip (`EXPLAIN ANALYZE`, минимум из 7):
`sum(x)` — 255.3 → 201.5 мс (−21.1 %), `count(*)` — 120.9 → 121.8 мс (+0.7 %).

### Главное наблюдение

Экономия на одном detoast **не постоянна**: 10–12 нс, когда выражение простое,
и 2–4 нс, когда в строке уже есть два-три других `palloc`. Копия сама по себе стоит
столько же, но в арифметически нагруженном выражении её латентность **прячется** за
внеочередным исполнением — процессору есть чем заняться, пока идёт `AllocSetAlloc`.
В дешёвом выражении прятать нечего, и цена вылезает целиком.

Практический вывод для статьи: `PG_DETOAST_DATUM` больнее всего бьёт по самым простым
запросам, а не по самым тяжёлым. Это контринтуитивно и стоит того, чтобы сказать вслух.

## Промахи мимо `shared_buffers`

`shared_buffers=32MB`, без prewarm — каждая страница читается заново (из page cache ОС,
не с диска). 11 повторов.

| запрос | detoast/строку | packed, мс | plain, мс | дельта |
|---|---|---|---|---|
| `count(*)` | 0 | 243.6 | 255.9 | **+4.9 %** |
| `sum(x)` | 1 | 306.5 | 268.5 | −12.9 % |
| `count(*) WHERE x>500000` | 1 | 331.3 | 292.9 | −12.2 % |
| `sum(x+y)` | 2 | 498.9 | 478.9 | −2.7 % |
| `sum(x*y+x)` | 3 | 623.0 | 585.4 | −6.3 % |
| `sum(x+y+x+y)` | 4 | 803.8 | 757.3 | −5.5 % |

`I/O Timings: shared read` — 72.3 мс против 83.5 мс, ровно +15.5 %: масштабируется
по числу страниц, как и должно.

## Точка безубыточности

Лишние 38.6 MiB на сканирование против сэкономленного CPU:

| запрос | экономия CPU | break-even по пропускной способности скана |
|---|---|---|
| `sum(x)` (1 detoast) | 50.9 мс | **759 MiB/s** |
| `sum(x+y)` (2 detoast) | 28.8 мс | **1341 MiB/s** |
| `count(*)` (0 detoast) | нет | PLAIN проигрывает всегда |

Читается так: выравнивание numeric окупается, только если данные лежат в памяти или на
NVMe. На сетевом хранилище или облачном диске на 250–500 MiB/s размен уходит в минус
даже для самого выгодного случая. Для запросов, которые numeric не трогают, он в минусе
безусловно.

## Контроль: правка `attstorage` прямо в каталоге

Возражение, которое напрашивается: а вдруг выигрыш даёт не физическая раскладка, а какая-то
ветка в пути чтения, которая смотрит на `attstorage`? Проверяется механически — меняем
`attstorage` в `pg_attribute` **не перезаписывая данные**, то есть меняем местами только ярлыки:

```sql
UPDATE pg_attribute SET attstorage='m' WHERE attrelid='t_plain'::regclass  AND attnum IN (2,3);
UPDATE pg_attribute SET attstorage='p' WHERE attrelid='t_packed'::regclass AND attnum IN (2,3);
```

На диске при этом по-прежнему: `t_packed` — 1B-заголовки, `t_plain` — 4B (проверено
`heap_page_item_attrs`). Новый бэкенд, свежий relcache, 9 повторов, минимум:

| запрос | как загружено | ярлыки переставлены |
|---|---|---|
| `count(*)` | +1.29 % | +3.34 % |
| `sum(x)` | **−26.58 %** | **−24.81 %** |
| `count(*) WHERE x>500000` | −23.29 % | −24.07 % |
| `sum(x+y)` | −6.27 % | −6.09 % |

Разница в пределах шума. **Путь чтения на `attstorage` не смотрит вообще** — всё решает
первый байт varlena в самом кортеже. Выигрыш чисто от физической раскладки.

Побочный вывод: пара «загрузить `COPY` при `PLAIN` → вернуть `attstorage='m'` в каталоге»
даёт тот самый гибрид «уже лежит выровненным, но колонка снова тоастится», которого
штатно не существует. Для эксперимента годится; как рецепт — нет, потому что любая
последующая запись в такую колонку снова начнёт паковать.

## Оговорки

* Один стенд, aarch64, 4 ядра. На x86 с другим аллокатором и другой памятью числа поедут.
* «Холодный» тест — это промахи мимо `shared_buffers` при попадании в page cache ОС,
  а не реальный диск: сбросить кэш ОС в песочнице без root нельзя. Дисковый случай
  оценён аналитически по числу страниц.
* `SET STORAGE PLAIN` отключает TOAST полностью: numeric без typmod может не влезть
  в страницу. Для бенчмарка неважно, для продакшена — стоп-фактор.
* Промежуточного режима «выровнено, но тоастится» в текущей инфраструктуре нет:
  `attispackable` — это ровно `attstorage != PLAIN`.
