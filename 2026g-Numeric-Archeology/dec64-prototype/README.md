# dec64 / dec128 — точные десятичные типы фиксированной точки

Расширение PostgreSQL: два яруса точного десятичного типа, воспроизводящих
лестницу DuckDB'шного `DECIMAL` настолько, насколько её вообще можно воспроизвести
в PostgreSQL.

| тип | байт | передача | цифр | масштаб | назначение |
|---|---|---|---|---|---|
| `dec64` | 8 | **по значению** | 18 | 0…7 | деньги: ISO 20022, DirectBank, ФФД |
| `dec128` | 16 | по ссылке | 37 | 0…15 | широкие форматы: ФНС ЭДО `N(26.11)` |

Написано как экспериментальная проверка к разбору
[fixed-point-for-postgres.md](../fixed-point-for-postgres.md).

**Итог: ×15 против `numeric` на арифметике у нижнего яруса, ×4 у верхнего,
при полном совпадении результатов с `numeric`.**

> ⚠️ Исследовательский код, а не готовый к эксплуатации тип. Ограничения — в конце.
> Расширение по историческим причинам называется `dec64`, хотя даёт оба типа.

---

## Представление

Оба яруса устроены одинаково: значение — масштабированное целое, масштаб живёт
**в младших битах самого значения**.

```
dec64:   1 бит знак + 3 бита масштаб + 60 бит магнитуда   →  18 цифр, масштаб 0..7
dec128:  1 бит знак + 4 бита масштаб + 123 бита магнитуда →  37 цифр, масштаб 0..15
```

**Почему масштаб в значении.** Output-функция получает только значение:
`dec64_out(dec64)`. Typmod-aware вывода в PostgreSQL нет вообще — `typmodout`
печатает сам typmod, а не значение с его учётом. Значит значение обязано уметь
напечатать себя само. Ровно поэтому `numeric` держит `dscale` в значении, `money`
берёт масштаб из `lc_monetary`, а `fixeddecimal` — из `#define`. Typmod вида
`dec64(p,s)` при этом поддержан, но как ограничение при присваивании — как у `numeric`.

**Почему 18 и 37, а не 38 как у DuckDB.** Один бит слова уходит под масштаб. У
`dec128` этот бит покупает масштаб до 15 — без него верхний ярус был бы бесполезен:
единственный нормированный денежный формат, выходящий за 18 цифр, — это `N(26.11)`
из схемы ФНС для ЭДО, где нужно **11 знаков после запятой**. Ярус на 38 цифр с
потолком в 7 знаков не покрыл бы единственный случай, ради которого он нужен.

```sql
CREATE TABLE fns(price dec128(26,11));
INSERT INTO fns VALUES (123456789012345.12345678901);
SELECT price, scale(price) FROM fns;
--  123456789012345.12345678901 | 11
```

**Почему два типа, а не один с двумя ширинами.** `pg_type.typlen` — одно значение
на тип, а не на typmod, поэтому ярус int16/int32/int64/int128 внутри одного типа
невозможен. Здесь это два типа, а переход между ними следует конвенции, которую
ядро уже применяет к `smallint`/`integer`/`bigint`: **операторы остаются в своём
ярусе и падают при переполнении, агрегаты поднимаются.**

`dec128` хранится как две половины по 64 бита, а не как поле `__int128`: датум
выровнен только на 8 байт, а разыменование невыровненного `__int128` — UB.

## Что взято у DuckDB

| решение | DuckDB | здесь |
|---|---|---|
| Представление | масштабированное целое | то же |
| Масштаб `+`/`-` | `max(s1,s2)` | то же |
| Масштаб `*` | `s1+s2` | то же |
| Переполнение | ошибка, тип не расширяется | то же |
| Масштаб произведения выше потолка | ошибка | ошибка |
| Агрегаты | накопление в 128 битах | то же, со сбросом в `numeric` |
| `NaN`, `±Infinity` | нет | нет |
| Специализация при связывании | bind-функция типа | `prosupport` (см. ниже) |

## Где сознательно разошлись

**Деление.** DuckDB возвращает `DOUBLE` из любого деления с decimal:

> «Division of fixed-point decimals does not typically produce numbers with finite
> decimal expansion. Therefore, DuckDB uses approximate floating-point arithmetic
> for all divisions that involve fixed-point decimals…»

Для типа, весь смысл которого — точность денежных величин, молча отдавать двоичную
плавающую точку из `total / count` — ловушка. Деление остаётся точно-типизированным,
на максимальном масштабе яруса, с округлением half-away-from-zero (регламент ЕС
1103/97 ст. 5, HMRC, п. 6 ст. 52 НК РФ):

```sql
SELECT '10.00'::dec64  / '3'::dec64;    -- 3.3333333            (масштаб 7)
SELECT '10.00'::dec128 / '3'::dec128;   -- 3.333333333333333    (масштаб 15)
```

У `dec128` нет более широкого промежуточного типа, который можно занять, поэтому
деление работает так: если сдвинутый числитель ещё помещается в 128 бит — одно
деление; иначе длинное деление по цифре. Быстрый путь покрывает практически все
реальные значения, и без него верхний ярус делил бы **медленнее** `numeric`
(2511 мс против 1737 на 20 млн строк — было измерено до того, как путь появился).

## Что умеет

Оба яруса: `+ - * / %`, унарные, `abs`, `sign`; полный набор сравнений с btree- и
hash-опклассами и `sortsupport`; `sum`, `avg`, `min`, `max` с параллельной
агрегацией; `round`, `trunc`, `ceil`, `floor`, `scale`; бинарный ввод-вывод;
typmod как ограничение; приведения к/от `numeric`, целых и плавающих; смешанная
арифметика с целыми, сохраняющая тип.

**Единое btree-семейство `dec_ops`** на оба яруса, так что кросс-ярусное сравнение
работает через индекс:

```
SET enable_seqscan = off;
EXPLAIN SELECT count(*) FROM t_dec64 WHERE v > '5.00'::dec128;
   ->  Parallel Index Only Scan using t_dec_v_idx on t_dec
         Index Cond: (v > '5.00'::dec128)
```

**Кросс-ярусные операторы объявлены явно** — и это не удобство, а необходимость:
без них `dec64 = dec128` неоднозначно, потому что `dec128 = dec128`,
`dec64 = numeric` и `numeric = dec128` одинаково хороши, каждый попадает ровно в
один аргумент. Кандидат, попадающий в оба, выигрывает сразу. Ядро несёт полную
матрицу `int2`/`int4`/`int8` по той же причине.

**Агрегаты поднимаются на ярус выше.** `sum`/`avg` копят в `__int128` и возвращают
`numeric`. У `dec128` значение само по себе заполняет 123 бита, поэтому у
аккумулятора есть точный «перенос» в `numeric`: когда очередное сложение не влезает,
быстрый 128-битный итог сбрасывается в перенос и обнуляется. На реальных данных
сброс не происходит никогда, на предельных — результат всё равно точен и неограничен:

```sql
SELECT sum(v) FROM (SELECT '9999999999999999999999999999999999999'::dec128 v
                    FROM generate_series(1,100)) s;
--  999999999999999999999999999999999999900     -- 39 цифр
```

**Функция поддержки планировщика.** Голая десятичная константа в SQL — это
`numeric`, поэтому `amount > 5.00` разбирается как `dec64 > numeric`.
`prosupport`-функция проверяет, представима ли константа в целевом типе точно, и
если да — переписывает вызов в одно-типовой оператор:

```
Index Cond: (v > '5.00'::dec64)          -- переписано
Index Cond: (v > 5.000000001)            -- не представимо, общий путь
```

Это ровно то, что DuckDB делает при связывании оператора, средствами, которые в
PostgreSQL уже есть. Без него сравнение с литералом было бы **в 1.7 раза медленнее**
`numeric`: построение `Numeric` на каждую строку дороже самого сравнения.

## Измерения

> PostgreSQL 20devel, Apple M4 Pro, 20 000 000 строк, значения 0.00…9.99,
> `jit=off`, один поток (кроме последней строки), лучшее из 3 прогонов.
> `dec64(18,2)`, `dec128(26,2)`, `numeric(18,2)`.

| запрос | `numeric` | `dec64` | `dec128` | dec64 | dec128 |
|---|---|---|---|---|---|
| размер отношения | 692 MB | 692 MB | 845 MB | — | — |
| `count(v)` — скан | 440.7 | 418.7 | 441.4 | — | — |
| `sum(v)` | 593.5 | 437.0 | 475.0 | ×1.4 | ×1.2 |
| `sum`, 8 сложений | 5100.7 | 723.4 | 1521.4 | ×7.1 | ×3.4 |
| `sum(v*v)` | 1299.7 | 494.1 | 747.5 | ×2.6 | ×1.7 |
| `sum(v/3)` | 1737.2 | 533.1 | 993.2 | ×3.3 | ×1.7 |
| `sum((v+v)*v-v)` | 2649.0 | 631.3 | 998.7 | ×4.2 | ×2.7 |
| `ORDER BY v LIMIT 10` | 859.0 | 396.9 | 620.9 | ×2.2 | ×1.4 |
| `WHERE v > 5.00` | 615.7 | 423.4 | 445.8 | ×1.5 | ×1.4 |
| `sum((v+v)*v-v)`, 2 воркера | 1059.3 | 213.9 | 358.4 | ×5.0 | ×3.0 |

Стоимость самих операций — вычтен скан, поделено на число операций:

| операция | `numeric` | `dec64` | `dec128` | dec64 | dec128 |
|---|---|---|---|---|---|
| сложение | 29.1 нс | **1.90 нс** | **6.75 нс** | ×15.3 | ×4.3 |
| умножение | 43.0 нс | **3.8 нс** | **15.3 нс** | ×11.3 | ×2.8 |
| деление | 64.8 нс | **5.7 нс** | **27.6 нс** | ×11.4 | ×2.3 |

### Что из этого следует

**Цена шестнадцати байт — примерно вчетверо.** `dec128` складывает за 6.75 нс
против 1.90 у `dec64`. Разница целиком в том, что 16 байт не помещаются в `Datum`:
тип передаётся по ссылке, и каждый результат стоит `palloc`. Убрать это нельзя —
`Datum` восемь байт. DuckDB платит тот же налог другой монетой: у него колонка
`DECIMAL(19,2)` сканируется примерно в сто раз медленнее, чем `DECIMAL(18,2)`.

**Но даже с этим налогом верхний ярус вчетверо быстрее `numeric`** — и это при
37 цифрах против 18, то есть на данных, которые нижнему ярусу недоступны вовсе.

**Хранение: 845 MB против 692.** Единственное место, где `dec128` дороже `numeric`
по памяти. Короткий `numeric` на денежных значениях укладывается в те же 8 байт,
что и `dec64`; 16-байтовый тип — нет.

**Узкое место — по-прежнему скан.** Даже самое тяжёлое выражение даёт ×4.2 у
нижнего яруса и ×2.7 у верхнего. Строчное хранилище остаётся строчным.

**Масштаб деления виден в результате** — и это не расхождение, а разные потолки:

```
sum(v/3):  numeric  -6309.35333333333320313478   (масштаб numeric)
           dec128   -6309.353333333332176        (масштаб 15)
           dec64    -6309.3532176                (масштаб 7)
```

## Корректность

`make installcheck` — два регрессионных набора, ~440 строк SQL: ввод-вывод и его
отказы, typmod и его нарушения, вся арифметика и её переполнения, сравнение,
хеширование, приведения, взаимодействие ярусов, округление, агрегаты (в том числе
параллельные и со сбросом переноса), btree- и hash-индексы, переписывание константы
планировщиком, бинарный ввод-вывод, формат `N(26.11)`.

Ключевая проверка — совпадение с `numeric` до последней цифры:

```
   sum    |        avg         | min  | max  | count
----------+--------------------+------+------+-------
 49950.00 | 4.9950000000000000 | 0.00 | 9.99 | 10000   -- dec64 / dec128
 49950.00 | 4.9950000000000000 | 0.00 | 9.99 | 10000   -- numeric
```

И классика:

```sql
SELECT '0.1'::dec64 + '0.1'::dec64 + '0.1'::dec64 - '0.3'::dec64;  -- 0.0
SELECT '0.70'::dec64 * '1.05'::dec64;                              -- 0.7350
```

Второе — расчёт налога из Decimal Arithmetic FAQ Майка Каулишо: `double` даёт
`0.73499999999999998667…` и после округления «до цента» теряет копейку на каждой
транзакции.

Набор поймал четыре настоящих дефекта:

1. **`ORDER BY` мог упасть.** Выравнивание масштабов при сравнении делалось в
   64 битах, и `999999999999999999` рядом с `0.0000001` давало «value out of range»
   при вполне определённом ответе. У `dec64` сравнение переведено в 128 бит; у
   `dec128` расширяться некуда, поэтому при переполнении выравнивания ответ
   выводится из знака: значение, которое не влезает при приведении к чужому
   масштабу, больше по модулю всего, что чужая сторона может держать. Арифметика
   при этом обязана ошибаться и дальше — точная сумма требует лишних цифр.
2. **Двойное округление** при `numeric → dec(p,s)`: сначала до потолка типа, потом
   до объявленного масштаба. `0.4449` превращалось в `0.45` вместо `0.44`. Лечится
   двухаргументной cast-функцией, получающей целевой typmod.
3. **Неоднозначность `dec64 = dec128`** — см. выше про кросс-ярусные операторы.
4. **Деление `dec128` медленнее `numeric`** — цикл по цифре без быстрого пути.

## Чего нет

- кросс-типовой **арифметики** с `numeric` и с плавающей точкой (сравнение есть,
  арифметика требует явного приведения);
- кросс-ярусной hash-семьи: `dec64` и `dec128` пакуют биты по-разному и хешируются
  по-разному, поэтому кросс-ярусные `=` намеренно **не** помечены `HASHES` — хеш-джойн
  между ярусами идёт через расширяющее приведение;
- обратной переходной функции у `sum`/`avg`, то есть оконные агрегаты с подвижной
  рамкой пересчитываются с нуля;
- `power`, `sqrt`, `log` — денежному типу не нужны;
- поддержки 32-битных сборок: `dec64` обязан помещаться в `Datum`, что проверяется
  `StaticAssertDecl`;
- расширенной статистики сверх стандартных `scalarltsel` и компании;
- вменяемого имени расширения: оно называется `dec64`, хотя даёт оба типа.

## Сборка

```sh
make PG_CONFIG=/path/to/pg_config
make install
make installcheck
```

По умолчанию `PG_CONFIG` берётся из `$HOME/pgdev-upstream/tmp_install/bin/pg_config`.
Требуется компилятор с нативным 128-битным целым (`PG_INT128_TYPE`).

```sql
CREATE EXTENSION dec64;

CREATE TABLE ledger (amount dec64(18,2), rate dec64(10,7));
CREATE TABLE invoice_line (price dec128(26,11));   -- формат ФНС для ЭДО
```
